# Agent 编排规则

## 覆盖状态与允许终态

`checkpoint.md` 为每个工作包维护人类可读状态：`未开始`、`进行中`、`已覆盖`、`部分覆盖`、
`无法取得`、`存在冲突`、`不适用`。状态由 Agent 根据证据判断；查询次数、文件数量、用户接受
限制或机械检查都不能自动提升状态。

- W0、W1、W9、W10 只允许以 `已覆盖` 定稿。
- W2–W5、W7、W8 允许 `已覆盖`、`部分覆盖`、`无法取得` 或 `存在冲突`。
- W6 还可在报告明确不形成预测或情景、W7 不使用前瞻输入且检查点记录具体理由时标记`不适用`。
- `无法取得`、`存在冲突` 和包内不适用子项必须记录替代、理由及对下游结论的影响。

## 依赖类型

- 开始前依赖：不满足时不能开展该包正式研究。
- 定稿前依赖：可以提前收集材料，但不能形成最终判断。
- 共享基准：不限制开始顺序，使用方必须引用同一明确事实；基准变化时全部复核。
- 回访触发：当前包的新证据真实命中正文条件时，由 Agent 判断并重开所列目标。

Python 只机械验证这些声明的结构和硬依赖无环，不执行依赖、回访、覆盖状态或 `required_when`。

## 自由编排

W0–W10 编号不代表顺序。W1 后，W2、W3、W4、W5、W8 可任意交错；W6、W7、W9 也可在
开始前依赖满足后提前收集材料，并在定稿依赖满足后定稿。Agent 可以合并支持多个包的工具调用、
按来源可得性调整顺序，并在宿主安全支持时选择独立研究并行；主 Agent 始终负责依赖、安全、
冲突合并、检查点和最终报告。

## 临时研究子问题

Agent 可把工作包临时拆成聚焦研究子问题并把结果汇回原包。临时问题没有稳定 ID、独立覆盖
状态或跨任务生命周期，不进入 catalog，不改变核心依赖和最低覆盖，也不能演变为代码执行 DAG。

## W2/W5 共享基准

W2 与 W5 共享同一份“截至 `as_of` 可得的最新已用披露”，不是顺序依赖。两包定稿时都记录
标题、期间、发布时间或仅日期保守判断及定位。任一方发现时点内更晚合格披露，立即更新基准、
撤销另一方旧终态并重查新基准之后至 `as_of` 的增量区间；`as_of` 后发布材料不能作为基准。

## 回访与递归失效

`may_reopen` 方向为当前包到可能被其新证据重开的目标，不表示反向关系，也不自动执行。触发
成立后，目标状态从任何终态变为 `进行中`，原结论标记“已失效待复核”；再依据定稿前依赖递归重开
结论可能受影响的下游。保留原状态、触发证据、受影响结论、重开目标、重新定稿结果和失败
历史。不受影响的包保留终态，但检查点记录简要依据。受影响包重新定稿前，W9/W10 不得使用旧结论。

## 用户可见进展

开始、主要覆盖变化、关键缺口、暂停或恢复、进入综合和交付前，用研究语言告诉用户当前目标、
主要进展、关键缺口与下一动作。不要只报告内部包编号，不公开状态协议或隐藏思维链。

## W10 停止条件

W10 开始前 W9 必须已覆盖；定稿前 W0–W9 必须达到各自允许终态，缺口和冲突影响已传播，
所有回访已重新定稿。两轮自检发现问题时只能：补查/修正并重开、披露非阻断缺口后收缩，或因
阻断项暂停/失败。研究与安全自检均完成、发布阻断问题为零、非阻断缺口已如实传播且报告实际
交付时，W10 才能以 `已覆盖` 停止。
