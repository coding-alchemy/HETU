## 1. 目标与实现边界

让用户在同等研究质量、工具调用与 token 用量受控的条件下，更快拿到完整报告，同时具备可靠的
任务控制、恢复、并行、资料复用、安装维护和宿主支持。耗时从用户请求至最终交付，包含准备、
独立核验与必要修正；代码、测试、进度消息和目录数量不代替这一结果。

沿用 Python 3.11／3.12、Typer、现有包校验、原子助手和 canonical Skill。主 Agent 继续承担
W0–W10 的研究决定，新增代码只负责明确的计量、文件操作和结构检查；宿主接入采用原生接口。
不新增模型 SDK、中央研究状态机、任务索引、代码调度 DAG、计费平台或第三方代码执行机制。

本轮仅新增计划并登记设计批准；没有运行股票分析、修改实现或认定产品通过验收。

## 3. 全局硬约束

1. W0–W10 身份、固定 owner、开始与定稿依赖、合法终态、回访传播和两轮自检保留。
   正式目录在 W1 唯一核验后创建；临时子问题不注册为核心工作包。
2. 适用必需项、请求与实际深度、点时、经营模型、反证、缺口和合法替代不变。W10 保留作者
   自检、新上下文独立证据核对、owner 修正、直接影响范围复查及安全自检。
3. 时间目标暂非 P0。仅超时记录实际耗时、卡点和剩余工作并继续，不暂停、降深度或请求续时。
   非时间预算、取消、能力、授权与安全停止条件仍生效。
4. `reuse_previous_task_data=true` 为默认；实际采用的许可允许资料复制到本任务，保留原来源
   与实际获取时间。`false` 排除旧下载资料、派生数据、研究脚本、报告、检查点和历史上下文；
   本次取得资料、本次重试／子任务／核验成果仍可用，正式 Skill、工具、依赖和有效授权仍可用。
5. 主体、时点、授权、核心事实、单位、否定、冲突、缺口、失效记录和用户决定在压缩及转交后
   可恢复；读取量限制每批内容，不删除必读项。Skill 正文不超过 500 行或 5,000 词。
6. 总调用与外部调用预算分开。输入、输出分别统计，缓存未知可缺省；金额不纳入精确统计，
   不以 token 总数抵扣一升一降，不把缓存命中解释为旧资料复用或服务端重新计算。
7. 四宿主为 Codex、Claude Code、OpenCode、ZCode；模型以实际响应或能力证据识别，CLI 名称
   不等于模型。未验证能力保留缺口，不以安装成功、CLI 退出或模拟测试认证正式支持。
8. 安装保留实体目录及既有路径，原子交换失败不先删旧版。扩展只含规则、声明、参考资料，
   默认禁用、按宿主绑定、不增授权、不覆盖核心、不执行附带程序或安装钩子。
9. 只保存必要脱敏证据，不保存隐藏思维链、凭据、无关日志或个人绝对路径。研究者与评审侧
   材料隔离；独立评分者不得参与作者修改或交付前核对。
10. 长期 1.7 完整监控规则排除；现有监控建议、复查与研究动作及长期 3.8 的语义保真照常验证。
    Python 不改指标、正负号、零分母、状态、窗口、连续期、AND/OR、来源和复查动作。
11. 本期承担长期第二、三章全部结果，具体资料与安全依赖须补齐；不把未通过的组合改为已支持，
    不因模块未成为主要瓶颈而省略功能。未经显式批准不使用 worktree，不自动切换模型。

已有“如有股票分析直接执行”等明确授权。不得通过称为 probe、子任务或核验绕过实际分析计数。

最终全流程性能比较为 standard 至少三对、quick／deep 各至少一对可比完整运行；五对并不

是五次基线加五次候选；并行专项、质量认证和支持组合需求先合并证据覆盖，再列最小新增量。

02 先完成首个获批样本，再检查完整时间、主研究／核对／修正／交付前协调用量和隔离。
合格即计入基线；不合格保存已交付质量与缺口，先修观测，不自动消耗剩余次数。不会因为
设计或计划尚未定稿而要求任何完整分析。性能数值在 02 根据有效基线提交用户确认；按 2026-09-11 performance-approval 批准，数值确认

## 5. 结果有效性与逐项重验审计

每阶段开工前在验收侧记录 `要求／case → 有效证据 → 具体行为变化 → 直接影响 → 最小验证`。
源研究、失败版本、评分与锁记录保留；需要新输出时使用新记录，不覆盖旧结果。以下规则适用于
全部任务，阶段文件再列具体失败条件；不能以“全量回归最安全”为由替代影响分析。

| 变化或缺口 | 可以做的最小验证 | 禁止推论 |
|---|---|---|
| usage 去重、字段或范围算法变化 | 对同一存活事件离线复算，补冲突和缺段反例 | 算法改动要求重跑原研究 |
| 历史日志缺失 | 保存可证小计与缺口；为新增指标另申请测量 | 缺日志使原质量结果失效，或用估计补成完整量 |
| 计时边界变化 | 有时间依据则重新计算；无依据则仅对应性能证据不足 | 以文件 mtime 补造请求或交付时间 |
| 控制、压缩或恢复行为变化 | 受影响指令及长材料短样本；直接受影响的完整 case 才另申请 | 修改 Skill 就全部重验 |
| 复用、复制、采用合同变化 | 有／无旧文件、许可限制、缺依赖与复制失败场景 | 强制给旧 manifest 补字段或全量重新下载 |
| 并行及汇合变化 | 独立域、依赖、冲突、失败和真实顺序对照 | 将他股并行或独立审稿计作单股并行 |
| 安装／启动器变化 | 临时目录、实际文件系统、故障注入及恢复后的版本 | 安装器升级使历史研究作废 |
| 扩展生命周期变化 | 受影响绑定、依赖、加载和安全场景 | 一个宿主更新导致所有宿主重新分析 |
| archive 读取／导出变化 | 原字段和源字节对照、危险路径、受限材料 | 恢复旧状态机或重建旧结论 |
| 质量修复 | 原作者局部修改，独立复查受影响维度并保留历史评分 | 修复后版本与原耗时自动组成合格基线 |
| 新宿主／新能力组合 | 映射已有可用行为证据，补该组合缺口 | 继承另一组合认证，或追溯否定旧组合 |
| 版本、模型、日期、分支、commit、哈希或 `as_of` 变化 | 记录来源、时点，按具体语义再判断影响 | 仅靠元数据让旧结果过期、绑定批次或整批重跑 |

哈希仅用于来源记录及检测同一已锁定产物后来是否修改；跨运行不以相同哈希证明等价，也不以
不同哈希判定失效。删除、覆盖或无法复核时只报告受影响证据，不伪造丢失记录。

## 6. 公共工程门禁与交付节奏

各任务先编写能暴露缺失能力的测试，再做最小实现，最后执行任务列出的定向验证。Prompt 修改
先列预期行为、条件／优先级／依赖和失败路径，再做隔离的正常、负向和边界试跑；字符串存在
检查不能代替行为。短样本、离线回放、真实完整研究三者分别标注，不互相冒充。

每个可独立审阅任务交付修改、定向结果、直接行为证据及剩余缺口；阶段收尾更新本路线图状态。
如提交，先查看 diff，只暂存本任务文件，不代提交用户改动、不使用 `git add .`；提交不代表验收。
完成必要检查后不无理由反复扩大测试。每阶段涉及代码的最终集成门禁为：

```bash
.venv/bin/python scripts/update_skill_manifest.py
bash scripts/check.sh
git diff --check
```

更新 manifest 后检查 diff 与本次 canonical 改动一致；新 manifest 未提交时，`check.sh` 中
`git diff --exit-code -- skills/hetu-stock-analysis/MANIFEST.json` 会按既有规则失败，不能删除该门禁。
先审阅并将本任务 manifest 与对应代码一起暂存或提交，再运行该门禁，确认没有未暂存漂移。
普通工程门禁不得启动真实股票分析，07 单独接入显式获批真实作业。

仅文档变更运行 `scripts/check_docs.py`、相对链接／冲突标记检查和 `git diff --check`。
未跟踪的新增计划也须显式纳入链接检查；不为写计划运行全套实现测试或股票研究。
