## 3. 候选问题逐项裁决

裁决标准：只有可定位的安全、错误统计、误判通过问题或阻止已选验收路径者纳入修复；
仅显示顺序、命名、诊断措辞或无关环境问题继续登记。复现均在临时目录
（`/tmp/hetu-verify-G5qNOt/`、`/tmp/hetu-offline-verify.kAKFRV/`）用合成数据完成，

### 3.1 扩展更新中断后同版本重试 —— 裁决：修复

- **有效要求**：「更新失败旧包可用」「更新失败恢复已批准绑定」「existing bindings stay
  untouched」（`src/hetu_stock/skill/extensions.py:546` docstring；旧阶段 06 计划合同）；
  `install_extension` 对同类残留先清理再建（`extensions.py:532-533`），update 路径不对称。
- **具体触发**：`update_extension` 在 `extensions.py:561` 执行 `target.mkdir(parents=True)`
  （无 `exist_ok` 且无前置清理）。首次更新在 mkdir 之后、`_commit_registry` 之前失败时，
  新版本半成品目录残留且未登记，同版本重试必抛 `FileExistsError`。
- **最小复现与观察**：合成 v0.1.0 安装＋codex 绑定，v0.2.0 候选，monkeypatch
  `shutil.copy2` 对新版本目标注入一次 `OSError`。观察：首更按注入失败；登记表、旧版本
  文件、绑定均字节不变（合同成立）；同版本重试抛 `FileExistsError`（非 `ExtensionError`
  子类），第三次重试仍被阻；CLI 受控 exit 1 但错误不指向恢复动作；无任何受支持命令可
  清理残留（`uninstall` 在有绑定时拒绝）；手工 `rmtree` 残留后重试成功、绑定仍旧版。
- **实际影响**：旧版本／绑定保护合同成立，无安全越界、无误判通过、无错误统计影响；
  但同版本重试被残留永久阻塞，用户须手工进入受管根删除半成品目录——超出纯措辞的
  实质性操作缺口，且与 install 的对称处理不一致。
- **建议**：修复（最小、对称 install），提案见 §5.1。

### 3.2 db-delivery 重跑及部分发布 —— 裁决：保留（继续登记）

- **有效要求**：发布／清理合同明确限定 db-export——「db-export 全部验证通过后才发布、
  写失败只清理本批半成品」（扩展计量批实现文档 §0、§2「6／发布与清理」）；登记本身注明
  「该命令不在修复批范围」（后半去向 §4 第 8 项）。db-delivery 的硬保证为 `_write_json`
  的 create-only 原子发布（`scripts/host_acceptance.py:1018-1048`）。
- **具体触发**：同一证据目录重跑 db-delivery；或目录只预置上次半成品 basis。
- **最小复现与观察**：合成交付事件＋临时输出目录。首跑 exit 0 正常发布；重跑 exit 1，
  未捕获 Traceback 末行 `FileExistsError: refusing to overwrite existing file`（抛自
  `host_acceptance.py:1027`），两份既有产物逐字节不变；预置旧 basis 场景下本批新建
  observation 残留、目录呈混合态但残留文件本身原子完整。对照 sweep／db-export 重跑为
  exit 2 单行清洁拒绝。「不一致」的具体形态＝未捕获 Traceback＋exit 1，且无 db-export
  式本批半成品清理。
- **实际影响**：create-only 由 `os.link` 保证，重跑绝不覆盖既有字节，错误可定位到文件；
  无错误统计、无误判通过、无数据完整性失真；basis 是 check 不消费的旁证文件；交付端点
  主通道为 sweep，不阻止本次验收路径。属仅不一致的拒绝风格。
- **建议**：保留。行为 fail-closed 且可定位；唯二适用的发布／清理合同均限定 db-export；
  登记已声明不在修复批范围。可作为非阻断后续清理项（重跑前置存在性检查＋exit 2；
  第二次写失败清理本批 observation），本次不修。

### 3.3 NULL started_at 记录的窗口归属与完整性 —— 裁决：修复

- **有效要求**：「未知状态、缺字段、占位零不能静默过滤」（计量完整性修复计划合同）；
  「无法证明结算时拒绝完整导出」（扩展计量批实现文档 §0、§2「6／计量归属」）；本阶段
  约束「不得给未知记录伪造窗口归属」（阶段 01 计划）。
- **具体触发**：声明会话 `model_usage` 存在 `started_at IS NULL` 的行（其余字段合法）。
  窗口查询 `WHERE session_id = ? AND started_at >= ?`（`host_acceptance.py:2100-2108`；
  tool_usage 同谓词 `:2265-2270`）按 SQL 三值逻辑静默滤除 NULL 行；
  `_zcode_db_check_schema`（`:2016-2033`）只查列存在性、不查 NULL。
- **最小复现与观察**：合成库同一会话 2 条正常行＋1 条 `started=None` 行（结算证据与
  行值一致）。db-export exit 0、「wrote 2 event(s)」、stderr 为空，NULL 行被静默排除、
  provenance 只记导出集，无任何提示；仅 NULL 行场景 exit 1 拒绝成立但理由失实
  （报「计量缺失」，实际行存在只是无法归窗）。
- **实际影响**：窗口内行的结算验证与拒绝逻辑全部正确，无错误统计；问题在完整性声明
  失真——对声明会话产出「完整导出」外观却静默遗漏窗口归属不可证明的行，违反
  「未知不得静默过滤、无法证明时拒绝」合同。属 schema 漂移暴露（登记注明真实库该列
  全量非空），不阻止本次验收路径，但合同违反可定位。
- **建议**：修复（拒绝而非归窗，不伪造窗口归属），提案见 §5.2。

### 3.4 validate 对畸形登记表的错误归因 —— 裁决：保留（继续登记）

- **有效要求**：「硬依赖缺失、完整性破坏、兼容性不满足时候选整体关闭并给出可定位原因」
  （扩展计量批实现文档 §2「5／失败关闭」）；畸形登记表合同为 `_read_registry` 抛
  「登记表不可读／格式无效」（`extensions.py:116-118`）；阶段 01 计划明确「纯诊断问题
  可保留，不改为默认阻断」。
- **具体触发**：`validate_extension` 经 `_registered_provides()`（`extensions.py:374-383`）
  用 `contextlib.suppress(ExtensionError)` 把畸形登记表吞成空集合；候选有未满足硬依赖时
  真实原因（登记表坏）被报成「硬依赖缺失」。
- **最小复现与观察**：合法候选（缺依赖／自足两种）×三种畸形表（非法 JSON、结构畸形、
  字段类型错误）。畸形表下缺依赖候选一律报「硬依赖缺失」（归因错误）；自足候选照常通过；
  同一张坏表在 install 等直接读表路径正确报「登记表不可读」。
- **实际影响**：fail-closed 成立、无误判通过——provides 只会变少不会变多，判定只会更严；
  validate 不写登记表，无安全与统计影响；误导不扩散（跑一次管理命令即定位真因）。
- **建议**：保留。拒绝边界与失败关闭均正确，问题仅限原因文案归类；改动 `suppress`
  语义属行为变更须另行批准，不在本轮范围。
