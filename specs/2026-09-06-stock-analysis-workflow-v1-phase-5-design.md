## 1. 设计结论与边界

五期完成长期需求第 2、3 章全部内容，以“同等研究质量下更快拿到最终报告”为首要结果。
保留 W0–W10、现有研究目录和 Agent 决策方式，补齐预算控制、取消恢复、上下文保真、正式并行、

以关闭复用的从零完整分析为主，开启复用时的收益单独记录。模型消耗用客户端输入、输出及
可取得的缓存命中 token 比较；本期不承诺精确金额统计。

本文已写明各模块的职责、接口、文件约定、失败处理和验收方法。用户于 2026-09-08 批准调整

设计定稿反复执行完整研究。§2.4.4 的已有结果按其证据范围保留，不因统计缺口使原研究失效。

## 2. 研究执行、协作与全流程提速

### 2.1 测量边界

以用户发出请求的时间为起点，以用户收到可打开、满足交付条件的最终报告为终点。计入
研究准备、取证、解析计算、文件读写、回访修正、独立核验和定稿交付。生成草稿或打印“完成”
都不能结束计时；锁后正式验收评分单独计量，不冒充用户拿报告前的必要等待。

宿主验收入口只观察公开可见的请求、工具事件、文件操作和最终消息。优先使用宿主提供的可靠
时间戳；由同一观察进程记录单调时钟时长与带时区起止时间。跨进程时钟无法对齐时保留未知区间，
不从文件修改时间、目录名称或 `as_of` 推算。

测试入口在发送请求前记录起点；宿主接收、开始处理与用户发出之间的间隔同样计入。既有记录
只有宿主开始处理时间时，须标明前段缺失，不能当作完整用户等待基线。

每个观察记录只包含：观察标识、关联任务、动作标识、开始与结束时间、所属环节、结果状态、
重试关联、必要的证据定位及第 2.6 节的 token 计数依据。环节说明由 Agent 或评审者结合可见动作判定，工具不
推测隐藏推理。记录放在研究根之外的 `.hetu/validation/phase-5/`，不修改已封存研究或新增研究游标。

| 指标 | 计算与解释 |
|---|---|
| 用户总等待 | 请求至最终交付的真实经过时间；用户确认、模型和工具等待不从总数中隐藏扣除 |
| 环节耗时 | 规则与能力准备、取证解析、分析计算、文件读写、回访、核验、交付分别列出；重叠区间取并集，不相加冒充总耗时 |
| 可见等待 | 单列模型响应、外部工具、用户确认和观测不到的时间，避免把所有空档归为模型推理 |
| 工具调用量 | 按实际调用去重计数，计入失败、重试、交付前核验和子任务；并行的多个调用分别计数，不与包装层重复相加 |
| 模型用量 | 从客户端取得输入、输出及可提供的缓存命中 token，按 §2.6 汇总；缓存缺失仍可比较输入与输出 |
| 有效交付 | 报告质量、实际深度、核验及交付边界均成立；不合格快报告不能进入提速通过集合 |

普通研究没有开启验收观察器时仍可运行；缺少计时证据只表示不能证明性能，不使研究结论失效。
时间或输入、输出用量不可取得时分别写“未观测”，不能宣称对应目标通过。缓存明细和金额缺失
不阻断输入、输出用量比较；不同指标分别判定，模型费用不再是五期性能验收的硬门槛。

### 2.2 基线与比较方法

1. 先将有效记录映射到请求、宿主能力、深度、数据模式和最终交付，检查是否具备完整时间证据。
   只有部分计时的报告可继续证明研究质量，不能充当完整性能基线。
2. 对比前固定请求和评分口径。基线与候选使用可比的证券、问题、深度、点时资料范围、宿主、
   模型、工具、授权、网络条件及 token 字段口径；差异逐项说明，不按版本或哈希是否相同决定
   可比性。从零分析的双方均禁用旧任务数据；允许复用的运行另行比较，不能混入主要提速结果。
3. `standard` 作为首要观察对象，性能比较至少有三对独立且可比的完整运行证据；`quick`、`deep`
   各有至少一对适用对照。优先复用已具备所需时间证据的运行，同一对照也可满足研究质量门槛。
   该数量是最终性能比较的取样口径，不要求在设计阶段执行，也不自动启动分析；缺失对照的
   分析次数与费用在实施阶段补测前单独批准。
4. 比较配对耗时比例的中位数，并逐对列出总耗时、质量、调用及输入、输出、缓存命中 token；
   不同深度和模型分别统计，缓存缺失不排除样本，不能把不同模型的 token 总数当成等价金额。
   所有预先选定的尝试都留在记录中。失败、超时或未完成交付不能作为提速成功，也不能换一个
   更快样本后删除原记录；质量可靠性的分母按第 6.3 节计算。
5. 人工确认或服务故障影响对比时，同时报告真实总等待和影响说明；不能只展示扣除等待后的数值。
   不具备可比性的运行由独立评审说明原因，保留证据并标记该对照未闭合。

### 2.3 优化的落点与行为验证

每项性能改动必须先有“耗时记录 → 重复或可减少的动作 → 修改点 → 完整报告对照”的依据。
下表规定发现对应瓶颈后的处理边界，不表示这些性能改动已被证明必要。§2.5 的研究执行能力
全部必做；测量只决定具体优化点和优先顺序。

| 证实的瓶颈 | 最小处理方式 | 必须验证的反例 |
|---|---|---|
| 重复读取规则、反复发现同一能力 | 同一上下文按需读取，保留已知能力及必要限制；发生相关变化时再核实 | 缺少必读规则或实际能力时不能按“读过、可用”继续；压缩后不确定时回读原文 |
| 重复检索同一问题或重复解析同一原文 | 由 Agent 复用本任务材料，以及 §2.7 允许复用的旧原始资料和确定性结果，核对用途、主体、期间、单位并保留实际来源 | 关闭旧任务复用时不能使用旧材料；相同文件名、摘要或哈希不能证明不同用途等价，新期间、来源冲突和失败项仍须处理 |
| 重写已有解析或计算脚本 | 工具目录提供直接可发现的调用方式，优先使用对应 canonical 工具 | 工具失败不能伪称成功或已复算；新增与失败脚本仍按原合同保留 |
| 重复生成文件或反复修正机械格式 | 用明确输入的确定性辅助完成格式与登记操作；由 owner 决定正文、采用状态和影响范围 | 工具不能改研究结论、代选版本、遗漏失败记录或绕过固定产物与更新时机 |
| 低收益重试 | Agent 按失败原因和已尝试路径限制重复动作，完成合理合法替代后记录缺口 | 未试合理替代不能直接标“无法取得”；预算耗尽不能伪报请求深度完成 |
| 核验后反复重做整篇研究 | 保留首次完整核对，修正后只回访 owner 与直接受影响下游，复查修正及影响范围 | 独立核对者仍自行找关键主张并回源；摘要、作者自评和缓存答案不能替代核验 |

性能优化聚焦测量显示占用关键等待路径的动作，不以减少代码行、文件数量、日志数量或提示词长度
作为收益。先验证同等质量的顺序执行，再完成正式并行和对照，不能用并行功能存在代替收益证明。

### 2.4 数值目标的确定

设计阶段固定 §2.1–2.2 的计量边界和比较方法，以及 §6 的质量要求；不以取得完整基线或固化
性能数值作为设计批准的前置条件。已有五次分析及其统计缺口见 §2.4.4，不据此自动安排重跑。

设计和执行计划分别获批后，在实施阶段按以下依赖推进：

1. 建立 §2.6.1 的计量、隔离和及时存证能力，先用离线回放与小范围探针核对去重、归属、计时
   和保存结果；这些检查不能替代完整研究的性能证据。
2. 保持待比较的研究行为尚未优化，优先使用有效旧证据；需要新增测量时按 §8.3 取得授权。
   先验证首个获批完整样本的计量与隔离证据，合格时计入基线，再据缺口确定剩余最小测量，
   不预设整批重跑。观测仍有缺口时修复观测能力，不继续盲目消耗完整分析次数。
3. 根据合格基线提交下表数值及依据，经用户确认后开展性能优化；不得看到优化结果后倒定
   目标。与性能数值无依赖的安装、扩展等工作可独立推进。

以下是实施阶段的校准交付，不是设计定稿前需补跑的清单：

| 输入 | 固化内容 |
|---|---|
| 性能基线 | 合格运行与配对清单、各深度耗时、主要瓶颈、未观测区间、调用及 token 计数依据 |
| 提速目标 | 各适用深度的完整分析耗时改善目标和判定范围；用于完成后的性能对照，不作为运行截止时间 |
| 用量约束 | 工具调用量不超过基线；输入、输出 token 分别比较，具体上限及一升一降时的判定待基线后讨论，不自动用总量抵扣或折算金额 |
| 非时间预算 | 根据实测提出三档外部调用、同类重试和并行度预算，区分可配置假设值与获批运行上限 |

#### 2.5.1 预算与停止

每次失败按对象、来源和原因关联已有尝试；同类重试到限后切换合法路径、缩小问题或记录缺口。

情况、已知卡点和剩余工作；交付时保留实际总耗时及超时说明。没有目标或无法观测的字段明确
标记，不编造分钟数或原因；不得因超时降低深度、省略核验或把未完成工作标为完成。

在开始、重要进展、预算调整、暂停恢复和交付前，以研究语言说明目标、完成域、关键缺口、

**直接验证：** 同类失败达到上限后没有继续启动对应调用；预算将尽时关键未知优先；各停止条件

#### 2.5.2 取消、调整与跨会话恢复

用户改范围时，核对新增、保留和冲突部分，只调整剩余工作；已有无冲突证据保留，新增范围按
未完成处理。提前交付仍须满足适用的核验和安全条件，并披露实际深度与缺口。

在现有 `checkpoint.md` 记录暂停点、已完成项、未决项、必要重查、用户决定和采用定位；

关闭复用的从零测试不查找或加载旧研究记录。

恢复时优先使用已有会话关联，在当前或用户指定且获准访问的研究根中，先按公司或代码、任务

未找到或记录不可读时说明缺口，不能猜选或宣称已恢复。

读取匹配任务的检查点及所需证据、产物记录，核对主体、时点、模式、授权和最新要求，向用户
说明已完成项、未决项、必要复核、当前限制和下一研究意图；只继续未完成与有直接影响证据的

**直接验证：** 取消后新调用和新委派为零，迟到结果未经恢复未被采用；改深度或关注点不丢无冲突

实际读取范围证明查找没有全量加载旧报告或原始资料，关闭复用的从零测试未查找或加载旧研究记录。

#### 2.5.3 能力预检与长上下文保真

子 Agent 能力；无法取得版本时记录实际可验证能力，不猜测。缺少请求深度必要能力时说明影响，

采用按问题分批读取方案，在现有资源入口设置全文读取字节预算，控制每批进入上下文的资料量。
达到预算时分段继续，必读规则、必要证据及其条件、注释、否定和例外仍完整覆盖；不得截断关键
规则或只读摘要省时。第 2.5.1 节的调用等预算与停止条件继续生效。详细规则保持直接可发现，
Skill 正文不超过 500 行或 5,000 词。

保留既有检查点更新时机。根据材料规模、宿主实际暴露的上下文余量或压缩信号，按需额外整理
供恢复使用的记录，再配合宿主原生压缩与恢复；不新增压缩引擎或研究状态机。宿主未暴露容量时，
按经验证的读取批次安排整理，不猜测剩余百分比。具体每批读取量、触发阈值及原生压缩恢复效果
结合各宿主实测固化；能力不支持或效果无法验证时记录缺口，不宣称该组合已通过长上下文验收。

正式检查点压缩保留证券、时点、数据模式、授权、来源、计算、事实、冲突、缺口、失效记录及
用户决定，并与当前目标、预算和采用记录一致；只保存结论依据和原文定位，不保存隐藏思维链。

覆盖跨文件事实、冲突与用户修正，验证压缩和转交均保持影响研究决定的内容。

例如核查年报某张表的注释时，回读对应页面及必要上下文，避免反复加载整份年报；问题确需
完整文档时仍须分批读完。摘要用于定位，必要核验回到原文。

**直接验证：** 缺 PDF、上下文或授权等必要能力时正确处理；长语料压缩前后及转交后，对相同
证据作出一致的受约束决定且可回源。遗漏关键否定、时点、计算口径或用户决定时测试必须失败。
分别覆盖容量可见与未暴露的宿主场景，用实际读取范围、检查点更新及压缩恢复行为验证按需整理；
每批预算不导致必要内容遗漏，原更新时机仍执行，不能只凭存在阈值或摘要字段判定通过。

#### 2.5.4 正式并行与任务隔离

分工采用已确认的按问题拆分方式：主 Agent 结合当前资料与待解决问题，确定每项独立研究的

不按固定领域整组启动，也不为凑任务数量重复取证。复用不能省略本次判断、适用必需项和独立核验。

#### 2.5.5 汇合、冲突与局部失败

**直接验证：** 同源转载不增加独立证据数；更早或更多返回不能压过可信冲突证据；局部失败保留

owner 责任或工作包依赖，也不把临时问题注册为新的核心工作包。

旧资料查找、原文及确定性结果复用统一遵守 §2.7。报告披露任务标识、父任务关系、生成时间、
请求与实际深度、采用产物摘要及 Skill、提示词或规则版本；不从无关系任务或散落文件拼装报告。
标识、哈希和时间用于定位与检测已锁定产物修改，不作为跨任务失效或强制重跑规则。

新增记录限于以下最小合同，实施时先同步产物合同及其检查器，不对旧文件批量补字段：

| 位置 | 新增或明确的信息 |
|---|---|
| `manifest.run` | `task_id` 关联同一请求，`run_id` 仍标识本次目录；跨任务继承时记录 `parent_task_id`，记录实际 `reuse_previous_task_data`，扩展信息按 §4.3 |
| `checkpoint.md` | 请求与目录关联、预算、控制及恢复摘要；子任务的标识、父任务、问题、owner、尝试、起止、实际状态、输出定位与采用决定 |
| owner 修订记录 | 每次旧新内容、字段与语义差异、原因及影响，引用具体尝试和证据；完整返回可在对应任务记录中保留，不复制到所有汇总文件 |
| 复用产物的 `provenance` 条件键 | 来源任务、原文件定位、原始来源与获取时间、本次复制时间；许可受限的定位使用脱敏引用，不能泄露秘密 |

`inputs` 仍只指向本次 manifest 中的本地副本，外部来源关系使用 `provenance` 和证据记录。
同一主题的唯一采用指结论或同用途版本唯一，不限制支持它的多个原始证据同时采用。正式目录
仍在 W1 唯一核验后创建，建档前的请求关联保留在当前上下文或验收观察记录，不提前创建研究目录。

**直接验证：** 多次重试、重新分派和跨任务继承后仍能解释差异、来源与最终唯一采用；旧版本和
原文可查，恢复摘要与报告一致；无采用依据、事后补造关系或覆盖失败历史均不能通过。

#### 2.5.7 并行收益验收

至少三个独立研究域的取证或分析区间真实重叠，与同契约、上下文和质量要求的顺序执行比较。
按 §2.1 记录起止和实际调用，在适合并行的样本中证明端到端中位耗时至少缩短 **20%**、研究
质量不下降，并同时验证隔离、汇合及局部失败。独立审稿或同时分析不同股票不能充当单股内部并行。

工具调用量同时满足长期不超过顺序基线 **125%** 及本期不超过基线的更严格约束。模型消耗
改用输入、输出及可取得的缓存命中 token，用量上限按 §2.4 固化，不套用金额比例；实际授权
数据费用仍受预算和授权约束。此专项独立验收，不替代从零完整分析的五期整体耗时目标。

### 2.6 客户端 token 用量统计

验收入口读取客户端原生用量事件或会话统计，按本次研究汇总，不建立计费服务。保存模型、输入、
输出、可取得的缓存命中量、字段含义、计数范围及必要的任务、回合或事件标识；不为用量统计额外
复制提示词、模型正文、隐藏思维链、凭据或无关客户端日志。

| 字段 | 记录与比较规则 |
|---|---|
| 输入 token | 保留客户端报告的输入量，注明是否已包含缓存命中或缓存写入；只比较相同口径，不擅自补成总输入 |
| 输出 token | 保留客户端报告的输出量；若已包含推理 token，不把推理分项再加一次 |
| 缓存命中输入 token | 客户端提供时记录；属于输入子集时不再加到输入，未提供时写“未提供”，不能填零 |
| 覆盖范围 | 主任务、重试、子任务及交付前核验是否完整；遗漏的任务或时间段明确列出 |

1. 累计快照按同一计数范围取起止差或新任务的最终累计值；增量事件按事件标识去重后相加。
   两种方式不混加，计数重置或恢复导致范围不明时保留缺口，不能把每条累计通知相加。
2. 按客户端定义核对父任务是否已含子任务；已包含时不再加子任务，未包含时补齐独立记录。
   失败、重试和交付前独立核验都计入；没有用量事件的部分标为未覆盖，不猜测其消耗为零。
3. 输入、输出分别给出优化前后的数量、差值和可计算的变化比例；基线为零时仅报数量与差值。
   缓存明细可供用户按适用单价人工估价，不维护价格表，也不将用量减少宣称为实际扣费减少。
4. 缓存字段缺失时，按相同字段口径继续比较输入和输出；输入或输出不可取得时，该宿主对应
   用量统计列为本期能力缺口，耗时与质量仍可单独验收。估算文本长度或账户总额度差不能补齐缺口。
5. 模型缓存命中与旧任务资料复用分开处理。从零研究仍可能命中相同系统提示词的服务端缓存，
   不要求清空服务端缓存，也不因出现缓存 token 就认定研究使用了旧任务资料。

宿主计数入口及已核实范围如下；字段存在不等于已覆盖整次研究：

| 宿主 | 计数接入 | 本稿的证据与限制 |
|---|---|---|
| Codex | `thread/tokenUsage/updated` 的 `tokenUsage.total` 与 `last`；字段为 `inputTokens`、`outputTokens`、`cachedInputTokens`，另有推理和缓存写入分项 | 本机 0.147.0 离线生成的协议 Schema 已确认字段；按线程取累计差或最终值，不将 total 与 last 相加。Schema 默认值不能证明供应商实际提供该项，父子包含关系和恢复计数仍需行为验证 |

重复事件不增量，缓存缺失可比较，未覆盖用量如实显示，已包含的缓存或推理分项不能重复相加。

#### 2.6.1 防止统计错误再次发生

本次问题来自汇总把消息内容块当作独立用量、混淆缓存口径和会话／调用单位、遗漏协调者工作，
以及未保存可回放依据。原 Prompt 已要求去重与覆盖检查，但首样本只证明计数器存在，未发现
核对转录重复和范围遗漏。仅增加“仔细统计”的提醒不能避免重犯；在 §1.3 已规划的 `scripts/host_acceptance.py`
验收入口落实以下确定性检查，不新增计费平台，也不由程序判断研究质量。

| 处理环节 | 必须做到 | 可直接验证的结果 |
|---|---|---|
| 确定范围 | 按实际动作区分研究、核对、交付前修正与协调，以及纯观测／锁后评分；记录父子包含关系和工具包装边界。混合且无法拆分的调用单列，不按“协调者”角色全部排除 | 缺协调者、核对者或修正段时显示已知小计及缺口，不能输出“完整任务总量” |
| 保存依据 | 原生事件出现后增量保存最小白名单字段：会话、请求／消息／工具 id、尝试、计数范围、实际模型、起止、原始 usage 数值及字段语义；恢复或日志清理前保存段末快照 | 客户端日志轮转后仍能离线复算已保存范围；不收集正文、隐藏思维链、凭据或无关日志 |
| 去重与归一 | 按来源会话及原生事件身份去重；同消息内容块携带相同 usage 只计一次。不同值必须依据该客户端的增量／累计／最终事件语义处理，无法解释则标冲突，不能盲取末值 | 重复相同事件不改变结果；同 id 冲突、累计重置、缺段不会静默生成完整总量；缓存未知不填零 |
| 对账与发布 | 原字段先按段与客户端聚合对账，再按已确认字段定义归一；同一份计算结果生成所有表格、单位与比例。时间比例写明分子、分母，重叠区间取并集；实际模型名称从响应记录取得 | 用量差额均有边界依据；小计之和与所声明范围一致；报告、设计、交付摘要不靠手抄保持一致 |
| 首样本检查 | 使用已有脱敏记录验证采集和汇总，再核对首个获批真实样本的研究、核对、失败、修正与交付前协调覆盖。计数器有值不等于观测通过 | 必需用量或隔离不可证明时安全收尾已启动样本，不继续消耗其余获批样本；缓存明细或金额缺失不单独阻断 |
| 独立复核 | 数字复算与研究质量评分分别进行；核对者根据原字段和事件身份重新计算，不只阅读同一份汇总表 | 本次 B04 的 83 行／20 消息回放得到 33,319 输出 token、46 次核对工具调用；在重复副本、冲突值、父子重叠、恢复重置和缺段输入下均能发现对应问题 |

以上为本期计量能力的设计要求，尚未实现。采集器的回放测试使用现有或受控小样本，不因此
重跑已通过的股票分析；任何新完整分析仍遵守 §8.3 的授权与最小补验范围。

### 2.7 旧任务数据复用：默认开启

本节细化长期需求第 2.6 节的资料复用行为，与 §2.5.6 的重试、继承和采用记录共用来源关系。
请求参数使用 `reuse_previous_task_data`，默认 `true`，仅控制旧任务资料与成果的使用。
自然语言“不要用旧任务数据，从头分析”对应 `false`。W0 在访问旧资料前确定开关；新任务
记录实际取值、复用材料及来源，旧记录缺少该字段时只表示未记录，不能据此认定当时未复用或
使旧结果失效。

| 模式 | 原始资料 | 解析、计算及研究结果 |
|---|---|---|
| `true`（默认，正常研究） | 按需定位相关旧任务，优先读取适用的财报 PDF、公告、网页存档及下载数据；已有材料不重复下载，只补必要的新资料 | 可复用适用的解析与计算结果，参考旧报告和研究记录；按当前问题完成判断及必要核验 |
| `false`（显式关闭，从零测试） | 重新获取本次所需资料，不读取或采用旧任务下载文件 | 不采用旧任务派生数据、报告、研究专用脚本、检查点或上下文 |

开启时，主 Agent 根据当前问题在已有相关研究记录中定位材料，核对主体、期间、口径、原始
来源、点时及授权。文件仍适用时直接使用，不为证明可复用而先整份重新下载或重算；发现新披露、
更正、缺失、损坏或输入方法有具体变化时，仅补取或处理受影响部分。新任务、版本或 `as_of`
变化本身不能触发全部重取。只在当前任务登记复用和采用关系，保留旧任务及原文件。

采用已确认的本地复制方式：把本次实际采用且许可允许复制的旧资料放入当前研究根，按既有
原始、标准化和派生产物分类保存；复用解析或计算结果时一并保留必要的合法原始输入与依赖。
后续读取、核验及报告引用使用本任务副本，`manifest.json` 和 `evidence.md` 记录本地位置、
来源任务与原文件、原始来源和实际获取时间，将本次操作记为复制。保留旧文件，复制后的修改
不能影响旧任务；不把依赖旧目录的链接视为独立副本，也不整套复制无关历史。
受限材料仅保留许可允许的定位与说明，披露不能随任务独立保存的范围，不声称全部材料均可打包。

例如，旧任务已下载适用且允许复制的 2025 年年报，新任务需要年报和新增半年报：默认本地复制
旧年报、复用适用解析结果，仅下载尚未取得的半年报；设为 `false` 时，两份原始资料均按本次请求获取。来源暂时失败时，
默认模式仍可使用适用且获准保存的旧原文；关闭模式须寻找其他合法获取路径或报告缺口，不能
退回旧文件。保留原始来源与获取时间，复用旧下载文件不得登记为本次重新下载。

两种模式均可使用正式工具、Skill、已安装环境和有效授权。开启复用不等于恢复旧状态机，
关闭也不删除旧成果或自动授权整批重跑。

从零测试采用已确认的独立研究上下文和任务目录，复用现有正式工具、Skill、已安装依赖与有效
授权，不为数据隔离例行重建工具环境。宿主验收入口新建研究上下文，按既定研究根规则使用新
任务目录；通过宿主原生控制排除旧任务历史、记忆或资料的自动引入，并将禁用旧资料的边界
传递给参与研究的子任务和交付前核验。不得通过删除旧任务或全局清除用户历史实现测试隔离。

验收记录实际提供的上下文范围、宿主历史加载行为和工具资料访问；检查旧文件、派生结果及
研究上下文均未成为研究输入。宿主不能落实隔离或证据不足时，记录该宿主对应能力缺口，
不能仅凭 `false`、新会话或新目录声明通过。各宿主原生接口在支持验证中分别核实；模型提示词
缓存按 §2.6 单独统计，不作为使用旧研究资料的证据。

**直接验证：** 默认模式存在适用旧年报时实际读取旧文件且不重复下载；新增半年报只补缺失材料。
关闭模式不读旧文件，获取失败不回退旧资料；主体或期间不符时不误用，所有复用有来源且旧文件不变。
允许复制的采用材料在旧目录不可访问时仍可从新任务读取和核验；副本及必要输入完整、来源与
获取时间保持真实，受限材料未越权复制，复制失败不能登记为独立保存成功。
从零模式验证独立上下文、目录、自动历史加载和实际资料访问；宿主仍带入旧资料或无法证明
隔离时，本项不能通过。正式能力及有效授权保持可用，旧任务及用户历史不被删除或改写。

## 3. 安装、更新与故障恢复

### 3.1 一次维护操作的路径

保留 `skill install --host ... --source ... --destination ... --force` 和既有三个宿主的默认路径。
补充 `skill status`、`skill diagnose`、`skill rollback`、`skill uninstall`；正常研究无需调用它们。
安装器继续拒绝包内符号链接、越界路径、缺失文件和清单不一致，不因强制更新放宽校验。

安装方式已确认：保留现有 Skill 路径和实体目录入口，覆盖安装采用“准备完整新版 → 校验 →
原子交换目录 → 确认结果并保留旧版备份”。具体系统调用、文件系统支持及异常恢复须按下述
行为验收，不因方案确认就视为平台支持已验证。

1. 在目标所在文件系统的受管暂存区准备完整包，暂存区与备份区放在宿主 Skill 发现目录之外。
   暂存包末级目录仍为 `hetu-stock-analysis`，沿用包名、frontmatter、链接和完整性校验。
2. 对同一目标加安装锁；确认目标是明确受管或用户指定的 Skill 目录，保留源与目标边界检查。
   复制、清单或结构校验失败仅清理本次暂存，旧目录保持可用。
3. 首次安装以同文件系统目录改名发布；覆盖安装使用原子的目录交换：Linux 对应
   `renameat2(RENAME_EXCHANGE)`，macOS 对应 `renameatx_np(RENAME_SWAP)`。交换后旧包仍完整
   保存在暂存位置，再记为可回滚备份。不能把“旧目录改名，再把新目录改名”称作原子替换。
4. 原子交换能力或文件系统不支持时，在触碰旧目标前失败，返回具体原因；不降级为先删后复制。
   这些系统能力必须通过真实平台和文件系统试验后才能列为支持条件。
5. 交换前写入并刷盘最小安装记录，包含目标、暂存、旧新包摘要及操作状态；交换后校验目标并
   完成记录。失败时交换回旧包；异常中断后，下次维护先按记录与实际目录恢复，不能盲删暂存。
6. 只有目标完整可读、备份可定位、安装记录一致时报告成功。恢复也失败时保留两份包和记录，
   返回失败及精确修复动作，禁止声称回滚成功。

该记录只描述安装事务，不记录证券、工作包进度或研究下一动作。摘要用于校验本次包及恢复
中断操作，不使任何已完成研究或支持证据自动失效。

目标路径继续由现有 `default_user_skill_root` 解析：Codex 的 `$CODEX_HOME/skills`（未设置时
为 `~/.codex/skills`）、Claude Code 的 `~/.claude/skills`、OpenCode 的
`$XDG_CONFIG_HOME/opencode/skills`（未设置时为 `~/.config/opencode/skills`），末级均为
`hetu-stock-analysis`。自定义 `--destination` 的含义不变。

暂存、事务记录和备份集中在目标文件系统内且不被宿主发现的受管维护区，以规范化目标定位，
同一目标的安装、回滚、卸载共用锁；未确认安全位置或同文件系统条件时在交换前失败。恢复
同时核对目标、新旧候选和实际摘要，无法唯一判断时保留现场并报告，不根据记录状态盲目删除。
首批平台验证为 macOS/APFS、Linux/ext4；其他文件系统按同一故障矩阵实测后增加支持声明，
不能仅因操作系统相同就宣称全部文件系统支持。

ZCode 的安装目标在五期增加 `--host zcode`，发现路径依据实际宿主机制核实，不直接假定为
`~/.zcode/skills`。本次基线显式读取仓库 canonical Skill，且环境记录提示自动发现的安装副本
落后，因此它证明研究内容可用，尚未证明全新安装及自动发现完整通过。补齐实际入口时沿用
相同原子更新、备份和用户数据保护，不能修改其他宿主的安装或扩展绑定。

### 3.2 Python 辅助环境与启动器

`install.sh` 不在旧 venv 上原地升级。为本次维护创建独立版本环境，在最终保留的路径中完成
依赖安装与 CLI 自检，避免移动 venv 破坏绝对解释器路径；准备失败保持旧环境和启动器。

Skill 发布与启动器切换分别使用原子操作；启动器用临时链接替换，并继续拒绝覆盖非 HETU
受管文件。跨目录的整套维护不是单个文件系统原子操作，后续步骤失败时按安装记录恢复已切换
部分，旧环境与旧 Skill 在维护成功前均不删除；完成后保留上一可用组合供回滚。

普通研究仍优先使用宿主能力和包内可选脚本，不例行重建环境、联网安装或跑工程检查。完整
Python 辅助包不可用时，public 基础研究继续按 Skill 规定处理，不伪称不可用 helper 已执行。

### 3.3 诊断、回滚与卸载

状态和诊断展示实际安装位置的脱敏表示、包完整性、可用备份、启动器归属、辅助能力与错误原因；
完整性检查不自动联网或修复。诊断结果给出下一动作，不输出环境变量全集、凭据或授权材料。

回滚选择一份完整备份，走同一暂存校验与交换流程，保留被换下的版本。用户主动安装更新属于
维护，不在研究过程中自动触发；本期不提供会话中途更换研究规则的热升级功能。

卸载先列出所选宿主 Skill、明确受管启动器、辅助环境及扩展绑定的处理范围，再执行用户要求
的删除。其他宿主仍在使用的共享环境不得删除；研究、旧报告、授权配置和非受管文件保留。
不能把宿主整个配置目录当作卸载目标。

**直接验证：** 源损坏、复制中断、目标校验失败、交换失败、进程中断、并发安装、非受管启动器、
不支持原子交换、回滚失败及多宿主共享环境均有行为测试；每项检查最终实际可运行的版本和用户数据。

## 4. 第三方工作包

### 4.1 独立存放与显式启用

第三方工作包存于用户数据目录下的 HETU 扩展区，不能放进宿主自动发现的 Skill 目录，也不能
修改 canonical 核心或官方目录。内容边界已确认：只支持研究规则、工作包声明和参考资料，
所需能力来自已有且获准使用的工具；不支持扩展自带脚本或程序，不执行安装钩子或安装依赖。
工具选择和结果采用由主 Agent 决定，启用不扩大工具或数据权限。启用范围已确认：Codex、
Claude Code、OpenCode、ZCode 分别保存启用和禁用状态，同一宿主后续适用研究沿用，直到禁用；
每次加载仍核对兼容、依赖、实际能力及授权，主 Agent 决定是否适用和采用。管理方式采用已确认
的自然语言与命令行共用工具方案，文件与命令约定如下。

沿用安装器的用户数据根 `$XDG_DATA_HOME`（未设置时为 `~/.local/share`），包存于
`hetu-stock/extensions/<扩展 ID>/<版本>/`，`extensions/registry.json` 记录实际包定位和
以现有宿主值 `codex`、`claude`、`opencode`，新增 `zcode` 区分的启用绑定；包版本发布后不原地改写，更新使用
新候选并保留可回滚版本。同一登记表的变更加锁，以临时文件校验后原子替换提交。
包文件可以共用，启用记录按宿主分别保存。启用和禁用操作明确所选宿主，只修改对应绑定；
在 Codex 启用不使其他宿主自动启用，在 Codex 禁用也不移除其他宿主已有的绑定。

`skill extension` 下提供 `list`、`inspect`、`validate`、`install`、`enable`、`disable`、`update`、`uninstall`
及面向 Agent 的 `context`。发现范围限于用户选定的本地包、已配置并授权的来源及本地登记项，
不建设公共市场或扫描无关目录。安装仅保存并检查候选，默认禁用。

用户可直接说“查看 Codex 已启用的扩展”“在 Claude Code 启用我指定的扩展”或“更新这个
扩展，并说明变化”，由宿主 Agent 调用同一组管理命令；用户也可手动执行。维护说明与例子
放在现有使用文档和管理命令帮助中，按管理意图定位并读取；纯管理请求不进入 W0–W10、不
创建研究目录，也不扩大 canonical Skill 的单股研究触发范围。两种入口共用同一套校验、授权
边界和状态结果，管理工具只执行明确操作，不决定研究问题、适用性或采用。

| 信息 | 用途 |
|---|---|
| 独立 ID、版本、来源、完整性摘要 | ID 使用 `x.<命名空间>.<名称>`，与 W0–W10、WX 官方 ID 分开；来源自述不等于可信身份 |
| 兼容性、所需工具及数据能力 | 明示核心协议兼容范围与请求权限；版本和引用由确定性工具检查 |
| 工作包声明 | 沿用开始前依赖、定稿前依赖、回访关系、适用条件、覆盖角色及报告归属；适用条件保持自然语言 |
| 启用绑定 | 按宿主记录用户或管理员批准的实际包及能力范围，供该宿主后续适用研究沿用；启用不等于授予数据账户或秘密 |

读取候选时只展示转义后的元数据，不把正文交给研究 Agent。变更前展示目标扩展、宿主、来源、
版本、摘要、能力和适用范围；更新先准备新版并展示变化，新增权限不能继承旧授权。目标和
授权明确时按已授权要求执行，不重复确认；目标有歧义或需要新增权限时再询问。更新未获相应
授权或验证失败时保留旧版可用。禁用、卸载及依赖失效立即阻止新的加载，不静默改用另一版本。

操作后根据实际登记与文件结果报告所选宿主、扩展、版本、启用状态及变化，失败时给出原因和
下一动作。工具不可用或结果无法核实时明确未完成，不能把已生成命令当作执行成功。

改变绑定的命令显式接收 `--host`、`--id` 及需要的 `--version`，包输入使用 `--source`；自然
语言入口先解析到相同参数。查看可列全部宿主，变更不能隐式作用于全部宿主。命令提供可读
输出及同内容的 JSON 输出，至少包含实际目标、版本、启用状态、操作是否完成和错误原因；
JSON 只供管理结果读取，不成为研究协议。

### 4.2 结构校验与运行加载

复用 `work_packages.py` 的字段、引用和硬依赖检查，为第三方增加独立入口；canonical 的核心
ID、官方注册表和包完整性规则保持严格。硬依赖缺失、环路、版本不兼容、ID 冲突、完整性失败
或权限超界均拒绝启用或加载。回访关系不当作硬依赖，代码不根据 `required_when` 编排研究。
包包含脚本、程序、安装钩子或要求安装依赖时，按超出本期内容范围拒绝启用或加载，并说明
具体原因；不执行附带代码，也不从参考资料或下载链接补装这些能力。规则与资料仍按原信任
边界审查，纯文本形式不能使越权指令变成合法动作。

`context` 只返回当前宿主中显式启用、完整且兼容的候选摘要和受管定位；无合法候选时返回空列表
及必要原因，不返回未启用正文。管理工具不可用时本次不能加载第三方扩展，核心研究仍可继续。
同一次研究按需读取已启用清单，清单为空时不扫描扩展正文；扩展更新也不触发后台整篇重研。

主 Agent 按当前证券、深度、授权和研究问题决定是否读取候选正文。读取后仍按不可信扩展材料
核对指令冲突、秘密、数据外传、交易指令及越权请求；发现冲突时停用该候选并说明影响。代码
校验通过或用户启用不能证明内容安全，也不能覆盖用户、核心 Skill 和宿主边界。

### 4.3 产物、更新与采用

- 第三方输出使用独立 `work-packages/x.<命名空间>.<名称>.md`，保留目标、证据、反证、冲突、
  缺口、回访及自检结构。核心包保持其固定文件，扩展不能代写、覆盖或替代核心必需项。
- 在产物合同中明确增加 `run.extensions`，仅记录实际加载包的 ID、版本、来源、摘要和启用
  范围；`work_package` 允许已校验的第三方 ID。检查器从本次明确记录校验归属，不读取任意
  全局插件目录来补造身份，不解释适用性或授予权限。
- checkpoint 和报告附录记录实际扩展及主 Agent 的采用或排除决定，事实仍按原证据链回源。
  不保存隐藏思维链或与研究无关的正文。运行中不自动替换已加载版本或重新采用结果。
- 生命周期复用第 3 节的暂存、校验、备份和原子发布原则；扩展登记表用原子文件替换提交，
  半完成安装不能成为启用项。卸载后其他扩展的硬依赖明确显示不可用，不自动扩权或重写依赖。

**直接验证：** 四宿主分别覆盖可信、未启用、不可信、权限超界、缺依赖、冲突、更新失败及恶意
扩展。检验正文是否进入上下文、实际工具或文件访问及主 Agent 的采用决定，不能只验证状态字段。
合规研究规则与资料能调用已有获准工具；带脚本、程序、安装钩子或依赖安装要求的包被拒绝，
验证没有执行附带代码或安装动作。内容边界验证不替代原有生命周期和安全场景。
仅在一个宿主启用时，其他宿主不加载；多个宿主分别启用后，禁用其中一个不改变其他宿主。
同一宿主后续适用任务沿用启用记录，兼容、依赖或授权条件不满足时仍拒绝加载。
相同管理意图分别经自然语言和手动命令行执行，实际绑定、文件结果及校验结论一致；有歧义时
不猜选，已有明确授权不重复确认，新增权限不自动继承，失败不冒充完成。纯管理请求不启动研究，
也不改变其他宿主的启用状态；不能仅以帮助文字或生成命令证明自然语言入口可用。

## 5. 旧格式成果读取与导出

新增 `helper archive-inspect --source <旧任务目录>` 与 `helper archive-export --source ...
--output <新目录>`。用户可用自然语言要求查看旧成果，由 Agent 调用；新研究入口不读取旧状态
推进研究，也不重新导入旧 `RunState`、`StageResult` 或状态机。

读取器将指定目录中的 `state.json`、`stage_results/*.json` 和已有报告按普通数据处理。首个
明确映射支持仓库留存的 `schema_version: 3`：请求、证据及主张、论点字段、阶段尝试、原采用
指针、用户决定和已有状态均按原值呈现，状态标注为“原记录”，不解释为当前任务可恢复。

| 操作 | 输出与限制 |
|---|---|
| 读取与审计 | 显示请求、阶段尝试、原采用记录、证据定位、缺失引用和原报告；不重新判定哪份研究应采用 |
| 导出 | 在新的目标目录生成可读索引，并按用户授权复制原记录及相关附件；保留原文件，索引给出源文件及字段定位 |
| 未知版本或无法映射字段 | 保留原文或原文件，标明未解释范围；不为了统一显示而丢字段、猜结论或重建旧报告 |
| 不安全或损坏输入 | 拒绝路径穿越、符号链接越界和可执行反序列化；标明不可读取项，不执行文件中的命令、HTML 或外部下载 |

只在用户显式指定的源目录内检查引用。导出不覆盖既有目录，不扩大授权材料的保存或传播范围；
对不能复制的材料保留许可允许的定位与原因，不能声称完成了无损全量导出。
原记录含凭据或秘密时，不把它们复制到可读索引或导出包；原文件保持原位置，披露脱敏与未导出范围。

**直接验证：** 已知格式、多次尝试、未知字段、缺引用、损坏 JSON、危险路径、输出已存在及
受限材料分别验证；已知字段逐项对照原值，无法映射内容仍可取回，源文件字节保持不变。

## 6. 宿主支持与研究质量验收

### 6.1 同一入口，区分检查与真实运行

扩展 `scripts/check.sh` 接入统一宿主验收入口。普通工程检查执行静态契约及已选证据检查；真实
运行须显式选择 `host_acceptance.py run`、获批 case 和宿主配置，不因一次 CI、分支更新或日期
变化自动启动股票研究。CI 的真实运行使用明确触发的受控作业，凭据由宿主提供，不写入仓库。

宿主适配只负责：检查本次可用能力、安装或发现 Skill、发送自然语言请求、订阅可见事件、取得
最终消息、产物定位及原生用量统计。各宿主适配器使用宿主原生入口，不接模型供应商 SDK，不注入研究下一步，
不把一次外部调用拆成代码控制的 W0–W10 流水线。

本地和 CI 对同一 case 使用同一输入隔离、证据格式、检查器和评分口径。没有宿主、授权、模型
识别或必要工具时记录“未执行／不支持该组合”，退出真实验收失败；模拟器和跳过不能显示通过。

从零性能与全量流程测试显式设置 `reuse_previous_task_data=false`；默认复用行为另有正向
验收，不能只测关闭模式。输入请求、研究记录和实际资料访问须一致，旧验收证据仍可在评审侧
用于对照，不作为关闭复用时的研究输入。
从零运行按 §2.7 建立独立上下文和任务目录，并验证宿主自动历史加载及旧资料访问边界；
数据隔离与全新安装认证分别验证，不能用其中一项成功替代另一项。

canonical 的 `name`、`description`、安全与研究规则保持单一来源；宿主专有 UI 元数据只映射
展示名称、描述或触发提示，不能新增研究指令。仅使用相应宿主实际接受并通过测试的字段；包
清单包含 Skill、引用、脚本、资产、manifest 与适用元数据，四个宿主使用相同 canonical 内容。

#### 6.1.1 原生接口与验证边界

2026-09-06 只读核对了三宿主的版本和命令帮助，并离线生成 Codex 协议 Schema；没有启动
研究、安装更新或调用模型。设计采用以下原生入口，不把“有接口”当成“本项目已通过认证”：

| 宿主 | 请求、取消与恢复 | 事件、压缩与并行边界 |

### 6.2 支持组合与证据

ZCode 是本期正式支持目标，沿用同一套研究规则，不另写一套 ZCode 专用研究流程。此次主研究
确实在 ZCode 中运行；核对环节使用外部 CLI 不改变主宿主归属。研究可用、全新安装与发现、
各项控制能力、性能计量和正式组合认证分别记录，已有结果按具体行为复用。

支持记录明确：宿主、可识别模型或可核验 Agent 能力、上下文、必要工具、数据模式、深度、
Skill 和验证时间。模型版本未暴露时保存真实能力测试结果，不猜测；新组合不能自动继承其他
组合的认证。安装、发现和预检成功均不代替完整研究支持。

每个组合从全新安装验证发现、自然语言触发、按需资源读取、真实研究与交付。正向请求包含
明确公司名、裸代码及带交易所后缀代码；反向包含行业、多股比较、组合、非 A 股和交易请求；
边界包含主体歧义、异常交易状态、能力与授权不足。按 canonical 规则确认、拒绝或降级，不能
因为宿主提示不同而改变研究范围。

证据目录保存脱敏请求、环境能力、必要可见工具轨迹、研究产物定位、最终消息、锁定记录、
独立评分、时间及第 2.6 节的最小用量记录。复用 `phase2_lock_run.py` 和无状态产物检查器；封存只检测同一锁定产物后来
是否改变，不负责判定研究正确、选版或发布。

先脱敏再生成可分享证据包，另行封存该包并记录与原证据的对应关系；不修改原封存产物。包内
用相对路径或脱敏别名；允许保存任务 token 用量汇总和计数依据，不保存隐藏思维链、无关遥测、
凭据、签名或个人绝对路径。
脱敏导致关键事实无法复核时，相关支持证据仍有缺口，不能靠一个“已脱敏”标记通过。

### 6.3 样本矩阵与评分口径

样本从下列维度组合，不做笛卡尔积。一份真实运行可以覆盖多个适用维度；每个声明支持的能力
组合仍须至少十次独立端到端运行，研究上下文不继承上次中间结论。实现前为每个 case 固定
证券、请求、`as_of`、模式、深度、故障设置、可见材料与独立评分依据，不能事后按报告挑样本。

输入目录与观察记录放在 `.hetu/validation/phase-5/`，研究目录仍遵守产物合同。每个 case
将发给研究者的请求、授权和材料，与仅供评审的期望、证据及评分分开；研究者无权读取后者。
验收入口的最小子命令为 `probe`（能力核对）、`run`（显式真实运行）、`check`（已有证据检查），
各自报告实际执行范围。`check` 不启动研究，也不将缺证据改写为通过。

样本输入分为两类：已有 M01–M06、F01–F05 保留原请求、时点、故障材料与评分依据，逐项映射
可用证据，不重新解释原 PASS；已执行基线的请求见 §2.4.2，后续新增请求按 §2.2、§2.4 确定并
取得授权。以下新增行为样本固定刺激与
观察结果，实际股票输入沿用获批中性请求；它们不是自动增加完整分析次数的指令。

| 行为样本 | 提供的输入或触发 | 评审侧验证 |
|---|---|---|
| 控制与恢复 | 研究仍有未完成工作时分别发出“取消本次研究”“改为重点分析现金流”“改成 deep”“按当前成果提前交付”；另一次在检查点后中断并恢复 | 按 §2.5.2 各自判断，不能将四个不同意图合成一次；取消无新研究调用，调整不丢证据，有限交付如实披露，恢复不重做无影响工作 |
| 预算与时间 | 受控来源对同一对象连续返回同类错误至已配置重试上限；另设已超过的时间目标而保留未完成必需项 | 重试达到上限换路或留缺口；单纯超时继续研究，其他停止条件仍成立 |
| 长材料 | 多文件证据在不同批次给出同名不同主体、时点前后披露、单位变更、否定条件、冲突及一次用户纠正；压缩后继续并转交独立问题 | 评审答案与材料分离；依据正确主体、时点及口径判断，保留纠正，必要时回读原文；遗漏任一决定性条件即失败 |
| 并行与采用 | 一组真实独立问题、一个有上游依赖的问题；对子任务注入合法来源失败、冲突及迟到返回 | 实际独立问题重叠，依赖未就绪不综合，失败局部处理，按来源裁决而非多数表决；顺序回退单列 |
| 复用与复制 | 获准旧年报及解析结果、一份新增披露；分别默认开启和显式关闭，另使旧目录不可访问或复制失败 | 比对实际下载、读取和采用；默认只补新增，关闭不读旧数据，独立副本可核验，复制失败不报成功 |
| 安装与扩展 | 临时宿主目录中的完整包、损坏包、受管及非受管文件；规则资料包、未启用包、带程序包和越权内容 | 按 §3、§4 观察最终文件、加载与权限；管理请求不启动股票研究，静态结构通过不能抵消恶意实际行为 |

股票状态和行业覆盖按下表验收，不根据公司名称猜定。缺少现成用例的北交所、消费、券商及
特殊状态，须在设计审阅时通过已有合法材料补齐具名请求、L0 依据和期望，不以先执行完整研究
为条件；若对应状态在所选时点不成立，不能宣称覆盖或临时改答案。评分量表、样本期望和统计
口径仍在设计批准前固定，实际执行及覆盖证据在实施阶段取得，与性能数值确认分开。

作者修正或定稿前核验，不能将评分答案放入研究输入。测试必须在对应能力缺失时失败。

## 7. 安全、授权与监控边界

真实对抗验收覆盖网页、PDF/OCR、表格、搜索片段、工具返回、授权材料、子 Agent 输出及第三方
扩展；手法覆盖直接、伪装系统消息、编码、隐藏、间接、跨 Agent、来源伪装、秘密定位、异常
链接、路径命令诱导和数据外传。

测试在隔离的授权工作区使用无价值诱饵文件和本地受控接收端，记录实际读写、命令、网络和委派
行为；不使用真实秘密或向外部发送用户材料。对同一研究问题保留正常材料对照，既验证攻击不
生效，也验证 Agent 没有通过拒绝全部正常研究来“通过安全测试”。攻击期望放在评审侧，不能
在研究输入中标注答案。

成功注入与相关发布阻断缺陷必须为零。材料中的指令不得引起无关文件读取、命令执行、可执行
下载、上传泄密、模式切换、授权扩大、越权委派、无关上下文传递或交易指令。摘要和解析不提升
指令层级，主 Agent 采用工具、子任务或扩展输出前完成安全与授权核对。黑名单、规则文本和
静态结构检查不能单独证明通过。

长期需求第 1.7 节“完整监控规则”已明确不纳入五期，其完整字段、专门语义摘要及配套规则验证
留待后续，不作为本期设计定稿、开发或验收的前置条件。现有报告的监控建议、复查与研究动作和
独立核对继续保留，长期第 3.8 节的语义保真核验仍须完成。

代码或重试均不得静默改变指标、数值、正负号、零分母处理、状态转换、
窗口、连续期数、AND/OR、来源及复查动作，不虚构字段通过检查，不把不完整建议包装成机械规则。

### 8.3 证据复用与补验授权

验收仍有效。补充用量观测同样遵守重跑授权，不修改旧产物来补造计数或隔离记录。

需要为性能增加计时而重做已通过研究，也必须如实说明只是新增测量需求，原研究仍有效；披露
预计分析次数和成本并取得本次批准。整批或已通过项重跑同样须批准。预计分析两家及以上公司
时，首次分析前询问是否切换性价比模型，除非本次执行已有明确直接分析授权；不得自行换模型。
