## 1. 已批准的决定

用户于 2026-09-20 批准按**可独立交付的能力**拆分：

- **五期前半：功能基础交付**。从已实现内容中提取完整的用户行为、必要依赖、文档与有效证据。
- **五期后半：验证与性能重设计**。保存未完成的验证、性能要求及已知缺陷，重新设计其执行方式。

不按原阶段 01–04／05–07 截断，不以代码存在替代行为成立，不以部分交付改称五期整体完成。
后半仍属五期；本决定不新增第八阶段，也不自动将未完成要求移到六期或降为可选。
前半与后半的具体条款归属在拆分计划中一次列齐，由用户评审后生效。

## 3. 前后半的能力边界

| 能力 | 前半拟交付 | 后半保留 |
|---|---|---|
| 安装维护 | 原子安装、更新、诊断、备份恢复、卸载及用户数据保护；平台声明限已验证 macOS/APFS | Linux/ext4 及其他未经验证组合；不删除现有安全失败机制 |
| 旧成果 | 显式旧目录只读检查、未知内容保留、安全导出 | 无需为此引入新研究或恢复旧执行器 |
| 任务控制与协作 | 预算行为、取消调整、恢复、问题分工、隔离输出、依赖顺序、冲突汇合、局部失败与采用记录；逐宿主限定证据 | 未通过的原生压缩、委派及跨宿主能力；预算待校准数值保持未定，不编造默认值 |
| 复用及减少重复 | 默认复用／显式关闭、来源和许可内独立副本；共享取数、汇合不重做、核验后及时交付的行为 | 从零隔离的未覆盖信号、真实复用收益与全流程／并行性能数值 |
| 扩展 | 确定性管理生命周期；ZCode/Codex/OpenCode 已证明的加载、采用和撤销路径；其他管理行为按已有证据列明 | Claude E3A 和修复副本加载归因、Claude/ZCode 缺工具构造缺口；不宣称四宿主全通过 |
| 质量及支持 | 保留 W0–W10、独立核验、修正回验、安全和实际深度要求；已有证据按范围引用 | 完整宿主／模型支持认证及尚缺组合；688048 已有结论有效，未出现语义不外推 |
| 观察与计量 | 前半只迁入其正常功能必需的合同及工程检查，不依赖完整性能装置运行 | 完整宿主验收／计量程序、导出关联缺陷、未闭合统计范围及全部性能采样 |

完整行为要求不会因为表格缩写而消失：迁移清单须映射原需求／设计具体条款，以及正常、失败和安全路径。
范围拆分允许已验证的能力先交付；未验证的宿主路径不包装成前半完整能力。

## 5. 用户规定的顺序与门禁

1. 记录原则和问题，提交、推送现有成果与本次决策。
2. 固定来源标签及分支冻结规则。
3. 编写前半迁移计划，提交用户评审。此时只规划，不创建迁移分支。
4. 计划获批后创建新分支，迁移需求、设计、计划、实现、测试和必要证据，执行适度验证，通知用户人工确认。
5. 用户人工确认迁移结果后，才对新分支开展全面评审。迁移中的自检不冒充这次全面评审。

从主分支提取还是从开发分支减法，由迁移计划根据具体依赖说明；不整批移入后半，再通过改名掩盖范围。

## 6. 这次拆分的成功标准

1. 冻结来源在本地和远端可核对；现有成果未丢失，后续修改与原始证据分开。
2. 前半每项能力都有“要求→用户行为→实现／测试→已有证据→适用范围”；必要依赖全部随迁移交付。
3. 新分支在不读取 `zn_dev` 工作区、私人原始会话或未提交文件的条件下可安装、检查并运行对应功能。
4. 后半要求、已知缺陷及未完成状态有明确去向，不以缩小前半范围删除原要求。
5. 工程验证只覆盖迁移及直接影响，不自动启动模型会话、股票研究、真实安装更新或扩展绑定修改。
6. 到达用户人工确认门禁即结束迁移批次；确认后再全面评审，不循环追加验收范围。
