## 1. 核心结果与边界

把现有量化软件整理为可维护、可提交的交付：使用本地合格输入，可以通过网页或独立脚本完成定义、资格判断、信号、真实 RQAlpha 模拟、账户评价、持久任务、查看与导出；输入不足时准确拒绝，旧结果继续可读。

本期用合成事实和已存在的有效证据证明软件行为，不要求先解决全池历史数据，也不宣称完成真实策略验证或达到经济目标。原二期未完成的真实要求逐项转交新三、四期，原“二期整体未通过”的历史结论保留。

现金、多头、不加杠杆；沪深普通股含创业板、科创板；日线估值、周／月机制，低波动正式协议仍为月频。北交所、ETF、实盘和多市场交易不新增。继续使用当前 `zn_quant`，不创建分支或 worktree。

## 2. 保留及收口范围

| 原任务 | 本期应交付的软件行为 | 直接证据与收口检查 |
| --- | --- | --- |
| 01.1 定义与引擎准入 | 递归冻结、独立导出、许可记录、隔离环境、真实本地引擎及证据绑定 | 复用已决许可和准入记录；真实引擎机制案例不以 mock／skip 代替 |
| 01.2 数据资格机制 | 公开版本、原件校验、历史身份、逐对象／信号日期资格、完整月末、用途与缺口分离 | 未来版本、采集中断、未知行动、退出对象等反例；已实现的 CNInfo 规范化与有界导入保留，不能标成完整 PIT 已获支持 |
| 02 账户与执行 | 次日成交、T+1、涨跌停、整手、历史费用、滑点、退出目标、公司行动、股息税、现金／净值及发布 | 实际引擎轨迹与独立账本核对；信号／登记／除息／到账／可卖日期分开，毛净关系不重复扣费 |
| 03.1 与 03.2 软件部分 | 七方向候选台账、低波动共同信号、冻结协议、最多八次调度、预算与经济评价机制 | 保留 36 月、ddof=1、最低十分位、市值权重；成熟标签、同口径基准、评价锚点、阶段选择和重复执行保护 |
| 04 与 05 软件部分 | 正式页面、资格、worker、进度／取消／重开、同产物导出及 Notebook | 已有生产链路机制证据；免费失败不调用付费、关闭 LLM 仍工作；真实结果演示移交四期 |

上表每项只作三种处理：**已有有效证据则引用复用；有具体软件缺陷则本期最小修复；需要新外部数据则注明三／四期去向**。不把可离线解决的错误借数据延期，也不因分期调整重新审计所有假想风险。没有直接影响证据时，不补跑已通过案例。

现有记录中的除权日限制价格参考、现金处置与换股等支持边界必须分清：软件如何消费合法输入、遇到未知输入如何受限，属于本期；供应商能否提供字段及期间，属于三期；原研究实际持仓遇到相应事件时能否完成有效评价，属于四期。不能用“未知即拒绝”声称所有公司行动已支持，也不能在四期静默删除受影响历史证券。

## 3. 最小交付物与清理规则

保留现有模块和接口，不重建框架、不批量改名 `phase2-protocol.json`、研究 ID 或 `.hetu/.../phase2/`。这些名称记录原研究来源，不承担新分期编号语义。

收口形成一份 `specs/` 下的本期实现与验收记录，集中维护有效代码、支持范围、证据入口、未完成事项和提交清单；直接引用已有产物，不再抄写各轮过程报告。旧计划退为历史回源，当前结论只维护在该记录中。

| 内容 | 处置 |
| --- | --- |
| 已实现代码、必要测试、稳定 fixtures、锁文件、使用说明 | 按实际职责纳入提交，保留支持未来真实研究的现有代码；不以“数据尚未齐备”删除 |
| 已完成计划及反复执行记录 | 先保存可恢复原文和校验清单，再将有效结论转入实现记录；删除仅限已完成且不再承担待办职责的部分 |
| 未完成的数据、真实研究、真实网页验收 | 在本期交接表保留原要求／证据、新归属、未完成原因和恢复入口；后期计划尚未编写不阻止二期收口，也不将这些项勾成完成 |
| 临时下载、调试输出、重复临时脚本 | 逐项确认无生产／测试／证据引用、可恢复后清理；引用不明则保留并说明 |
| 原始响应、发布快照、研究结果、原件、失败／修订记录、预算台账 | 保留；不作为无效临时文件删除，不批量纳入源码提交 |
| 凭据、虚拟环境、缓存、市场大文件、无关工作区改动 | 不纳入本次提交；不得用 `git add .` 混入 |

重组前原文已保存于本地[清单](../.hetu/quant/acceptance/reorganization-20261021/manifest.json)。它包含未提交版本，不应误称可以从旧 Git 提交恢复。最终清理需再次确认待删原文与归档一致。

旧 01–05 混有已完成和未完成内容，不要求逐行删改成新计划。按获批收口计划完成上述转交、归档和链接更新后，可整体退出当前执行入口；未完事项继续由交接表追踪，后期编计划时接续。这样既不保留两套现行待办，也不以三、四期计划获批作为二期提交前提。

## 4. 验收与提交

| 编号 | 可观察的通过条件 |
| --- | --- |
| N2-1 | 第 2 节每项存在行为证据；无数据时显示具体资格缺口，不生成伪成功；许可及真实引擎机制证据可核查 |
| N2-2 | 用户可在网页提交受控机制任务、找回／取消、查看账户及导出；独立脚本、Notebook 读取同一合同，LLM 非必需 |
| N2-3 | 交接表引用总方案的完整映射，原二期未完成项均有原要求／证据、新归属、原因和恢复入口；旧结果与失败台账保留 |
| N2-4 | 必要修复的直接回归、适用工程检查通过；清理不删证据或唯一待办；提交清单排除凭据、大数据、环境及无关改动 |
| N2-5 | 按本次用户要求在当前分支提交有效内容，报告提交 ID、范围、剩余未提交项；不推送、不合入 main |

有效历史验证优先复用。文档重组本身不触发代码测试或真实研究；执行期仅按实际修改影响选择验证，不为取得一个更新的全套数字反复重刷。若新增代码缺陷，测试材料遵循项目方法论。

用户已经提出收口、清理和提交目标，并已指示编写本期独立收口计划；计划获批后实施，无需将其解释为再次讨论是否要提交。若目标分支变为 main 或提交范围实质改变，按 AGENTS.md 另行处理。当前设计及计划不代表本期验收通过。

## 5. 交接与设计取舍

交给三期：稳定的数据产品／版本／证据／资格合同、已有免费资产及真实失败样本。交给四期：引擎、冻结协议、独立研究入口、八次调度及基本网页。交给五期：同产物读写边界和现有工作台能力。

本设计选择“复用证据、关闭具体软件问题、一次收口提交”，不重建框架或重新执行全部验收。真实研究、原股票池和经济目标完整交接。后续计划只拆“范围与证据收口、必要修复与清理、验收与提交”三个单元；本节不替代计划审批。
