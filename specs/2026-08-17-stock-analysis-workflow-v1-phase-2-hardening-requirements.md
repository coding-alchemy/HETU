## 0. 二期结论

二期总体目标是加固现有工作流：先解决报告输出缺少稳定框架的问题，并纳入待讨论的质量加固
候选（第 10 章）。主目标是为 `quick`、`standard`、`deep` 建立统一、带序号、
可直接填充的 Markdown 主模板，并为三档分别定义必填内容和允许的展开程度。

三档报告共用同一章节骨架。请求深度只改变每章必须取得的数据、分析深度和证据强度，不得改变
章节顺序或通过省略章节隐藏缺口。模板保证覆盖稳定性，但不能替代事实核验；内容零错误仍是独立、
非补偿硬门禁。

二期同时承接 GLM 独立研究中发现的三个原子工具候选：财务报表标准化、公告索引标准化和数值
一致性校验。该工作只允许修复、测试和最小整合已经取得的公开数据，不扩张来源和研究结论控制面；
必须在模板主目标之后作为独立阶段执行。

来源扩张、经营模型适配、并行、复杂恢复、多宿主认证、安全评测和安装治理归入 V1 长期需求，
不得混入本期。

## 1. 前置条件与优先级

### 1.1 二期启动前提

1. 一期 Agent 主导研究闭环保持成立（见一期实现基线），不恢复 Python 或模板引擎对业务内容的控制权。
2. 历史代码精简已经完成全部串行阶段并取得用户确认，canonical Skill 效果没有退化。
3. 已保留本需求列出的三份参考报告，且只把它们用于结构、覆盖和信息量参考。

### 1.2 约束优先级

1. 报告中不得出现错误事实、数值、单位、期间、主体、范围、时点、计算或引用。
2. 每档报告必须遵循对应模板和必填内容，不得自由删减固定章节。
3. 缺口必须显式表达，不得为了填满模板猜测、补造或把未检索写成没有。
4. 可读性和篇幅优化不得覆盖前三项。

## 2. 二期范围

### 2.1 P0：二期必须完成

1. 建立一套统一主模板，固定报告标题、元数据、重要声明、核心发现表和编号章节。
2. 建立 `quick`、`standard`、`deep` 三档必填内容矩阵。
3. 统一“有、无、未发现、未取得、不适用、存在冲突”的填写语义。
4. 规定核心发现表、正文、证据记录和最终用户消息之间的一致性。
5. 以真实独立报告验证三档模板不会降低信息量或引入事实错误。

### 2.2 P1：分析工具候选修复与整合

P0 模板验收完成后，二期以独立阶段处理
[`../archive/phase4-analysis-tool-candidates/README.md`](../archive/phase4-analysis-tool-candidates/README.md)
中的候选，不得与模板修改捆绑验收：

1. 保留原始错误脚本的逐字取证副本、来源和 SHA-256，禁止直接执行或安装。
2. 仅评估并修复财务报表标准化、公告索引标准化和数值一致性校验三类原子能力。
3. 候选只处理已经合法取得的公开数据；不得在候选代码中新增网络采集、固定证券答案或来源优先级。
4. 完成已知错误、异常结构、时点、单位、分页和冲突场景的 RED→GREEN 测试后，才能提出 Skill
   接入设计。
5. 接入必须是可单独回退的最小变更，并经现有全门禁、真实多模型报告回归和用户人工确认。

### 2.3 二期不包含

1. 扩张数据源、行业专项模型、预测模型或估值能力；第 2.2 节只处理已有公开来源结果，不构成
   新来源建设。
2. 子 Agent 并行、复杂恢复、成本预算、跨宿主认证和第三方工作包治理。
3. 安装器、CLI、历史状态迁移或大范围代码架构重构；第 2.2 节经门禁批准的原子辅助函数除外。
4. Jinja、Python 报告生成器、固定业务 Schema 或由程序选择和拼接研究结论。
5. 修改三期历史报告或用人工修正后的报告冒充盲测结果。

上述增强统一由 V1 长期需求承接。

## 3. 统一输出框架

### 3.1 固定章节骨架

除报告主标题外，所有二级章节必须使用连续阿拉伯数字；存在三级章节时使用对应的 `x.y` 编号。
三档报告固定使用以下骨架：

1. 任务与时点
2. 核心发现
3. 公司、业务与行业
4. 治理、审计、资本配置与重大事件
5. 财务验证与经营质量
6. 预测与受限情景
7. 估值与隐含预期
8. 市场状态与近期信号
9. 论点、反证、未知与条件
10. 监控建议
11. 数据覆盖、缺口、冲突与来源
12. 最终边界

章节标题、编号和顺序不得由模型自由改写。某章没有适用事实或合法证据时仍保留章节，并按
第 5 章的状态语义填写。

### 3.2 报告首页

报告首页至少包含证券、`as_of`、报告实际分析或定稿时间、数据模式、请求深度、实际覆盖、技术
完成状态和重要声明。实际分析时间必须包含日期、时间和时区，能够区分不同运行与报告版本。

重要声明之后必须紧接“2. 核心发现”。核心发现使用固定维度表，至少覆盖：主体、核心业务、
收入或经营规模、利润或经营回报、现金或资产质量、治理与重大变更、并购与资本配置、估值与
市场状态、最强反证、关键验证点。不适用维度不得删除，须说明原因。

### 3.3 核心发现与正文一致性

1. 核心发现表只能压缩正文中已经取得证据支持的结论，不得出现正文没有的新事实、计算或判断。
2. 表内关键事实必须能在正文定位到展开分析和用户可读来源。
3. 最终用户消息只能复述 `report.md` 已有结论，不得在文件之外另行生成更完整的总结表或新增
   可交付事实。
4. 核心发现与正文冲突时不得交付，必须回到证据和对应章节修正后重新自检。

## 4. 三档报告约束

### 4.1 共同要求

三档都必须保留第 3.1 节全部章节、核心发现表、关键引用、最强支持、最强反证、最大未知、监控
和覆盖边界。深度较低只能减少展开和交叉验证，不得省略框架或把技术完成冒充信息完整。

### 4.2 Quick

`quick` 以快速形成可靠概览为目标，至少取得并填写：主体与交易状态、核心业务、最新财务概览、
最近重要公告、基本股本与行情、基础估值参照、最强支持、最强反证、最大未知、关键验证点和
主要数据缺口。无法形成预测、估值或监控时必须说明最小缺失输入，不得留空。

### 4.3 Standard

`standard` 是默认报告，必须在 `quick` 基础上实质覆盖：

1. 公司控制关系、业务结构、收入和成本驱动、行业与竞争及反方解释。
2. 治理、审计意见、关键审计事项、重要资本配置和基准日后重大事件。
3. 最新正式披露调整后的多年财务和最新一期，覆盖利润、现金、资产负债、营运资本、研发、
   并购商誉及其他适用的经营质量指标。
4. 有证据约束的情景、估值输入与口径、市场状态、支持、反证、未知、成立和失效条件。
5. 具备指标、窗口、来源和复查动作的监控建议，以及完整缺口、冲突和来源说明。

`standard` 的总有效数据量硬下界以
`.hetu/research/002371-20260815T211119+0800/report.md` 为准；
`.hetu/research/002371.SZ-2026-08-13-quality-recovery/report.md` 仅用于校验常规财务、经营、治理、
审计和证据引用等核心领域没有缺失，不要求机械合并两份报告的全部内容。行数、字数、重复表达
和无证据判断不能充当有效数据量。

### 4.4 Deep

`deep` 在 `standard` 全部要求之上，进一步覆盖更长历史周期、完整年报和重要附注、主要分部、
产业链与竞争者、更多独立来源、资本配置效果、预测敏感性、估值方法交叉和更细的证伪条件。
具体必填字段由二期设计按统一骨架展开，不得通过新增无编号自由章节实现。

## 5. 空值、缺口与重大变更语义

1. **有**：取得了与主体、期间、范围和来源一致的有效证据。
2. **无**：已完成规定范围的完整检索或核验，可以确认没有该事项。
3. **未发现**：只完成标题、索引或有限范围筛查，不能等价为绝对没有。
4. **未取得**：合法路径和合理替代后仍未取得所需证据，必须说明影响。
5. **不适用**：基于公司经营、会计或交易状态确实不适用，必须给出理由。
6. **存在冲突**：有效来源之间存在未裁决差异，必须保留双方口径及对结论的影响。

重大变更章节不得把“没有检索到”写成“无”。非重要、重复、流程性公告可以在正文省略，但必须
先完成规定窗口的公告筛查；省略不影响核心论点的公告不算信息量下降。

## 6. 质量与验收门禁

### 6.1 非补偿硬门禁

1. 任一固定章节缺失、编号错误或核心发现表缺失，报告不通过。
2. 任一写入报告的事实、数值、单位、期间、主体、范围、时点、计算或引用错误，报告不通过。
3. 任一必填维度被静默省略、用空泛文字占位或错误标记为“无/不适用”，报告不通过。
4. 核心发现、正文、证据和最终用户消息存在实质不一致，报告不通过。
5. 其他章节的信息增量不能补偿上述任何失败。

### 6.2 真实报告验收

1. `quick`、`standard`、`deep` 各执行至少一次全新目录、无答案提示的真实报告。
2. `standard` 使用同一中性请求在至少两个不同的支持模型上独立运行，验证框架和必填覆盖不会
   因模型不同而消失。
3. 每份候选记录实际分析时间、Skill 身份、模型、推理深度和可用工具；宿主不可见字段如实标记。
4. 候选先锁定再评审，不得原地人工补写；失败报告保留为失败证据。
5. 三档报告均通过自动结构检查、独立事实复核和用户人工确认后，二期才可完成。

## 7. 分析工具候选质量约束

### 7.1 已知错误必须进入回归

二期设计和计划必须覆盖以下已确认错误，不得只测试正常输入：

1. 东财字段序号被错误命名，导致营业收入、毛利率和资产负债率被写成其他指标。
2. 腾讯报价中的总市值和流通市值标签与股价乘对应股本的复算结果互换。
3. 不同来源、不同 Schema 的资金流数据覆盖同名文件。
4. 证券、日期和绝对路径硬编码，`as_of` 没有应用到所有时点敏感记录。
5. 原始响应、字段映射依据、HTTP/响应结构验证不足，巨潮入口存在 HTTP 和单页覆盖问题。
6. 最终产物依赖主脚本之外的补采脚本，单次运行不能完整复现。

### 7.2 候选职责边界

1. 候选可以做确定性解析、排序、时点过滤、精确算术和一致性比较。
2. 候选不得决定工作包是否覆盖、哪个来源更可信、冲突采用哪一方或报告写什么结论。
3. 数值冲突只能返回双方值、差异和是否超容差，禁止静默改写来源值。
4. 公告索引必须使用显式时区的 `as_of` 和 HTTPS，并暴露总数、返回数及分页是否完整。
5. 财务标准化必须保留来源原值和报告期，不得猜测同比、调整前后口径或字段语义。

### 7.3 正式整合门禁

1. 每个来源均有字段字典或一手字段依据；独立复算只能校验，不能替代完整字段合同。
2. 原始响应、标准化产物和来源元数据可重放；不同来源或 Schema 不得覆盖同名产物。
3. 测试覆盖已知错误、缺字段、错类型、零分母、单位、时区边界、`as_of` 前后和分页不完整。
4. 取证副本不进入安装包；候选在批准前不进入 canonical Skill 或 manifest。
5. Skill 接入另写设计和执行计划，保持最小可回退，并重新通过全门禁和真实多模型报告回归。
6. 用户人工确认模板效果和候选整合效果后，才能完成二期。

## 8. 二期完成定义与 V1 边界

二期只有同时满足以下条件才能结束：

1. 统一模板、三档必填矩阵和状态语义已经写入 canonical Skill 的按需报告资源。
2. 三档真实报告均保持固定编号结构，核心发现表位于重要声明之后。
3. `standard` 信息量不低于既有质量基线，全部候选报告没有事实错误。
4. 最终用户消息没有 `report.md` 之外的独有事实或总结。
5. 第 7 章候选通过修复、测试、最小接入和真实报告回归，不改变 Agent 对覆盖、来源和结论的控制权。
6. 用户分别确认三档报告及候选整合可用，并明确允许进入 V1。
7. 需求、设计、计划、Skill、manifest、测试和文档链接与实际状态一致。

V1 继续处理来源完整性、经营模型适配、并行、复杂恢复、多宿主认证、安全和安装治理；不得在
二期模板工作中提前实现这些增强。

## 9. 后续设计输入

二期设计只需进一步明确：

1. 主模板和三档内容矩阵在 Skill 中的具体资源位置及按需读取方式。
2. 每个固定章节的精确 Markdown 结构、核心发现表字段和各档最小展开要求。
3. 不同公司类型出现不适用项时的表达方式，不预先写入具体证券答案。
4. 结构一致性、事实正确性、信息量和最终消息一致性的验收方法。
5. 三档真实盲测的中性请求、模型组合、归档和用户放行方式。
6. 三个候选的字段合同、原始响应留存、输入输出、错误语义、回归场景和 Skill 最小接入点。

设计不得增加与模板或第 7 章候选无关的研究能力，也不得把自然语言报告改造成程序控制的业务
表单。

### 10.1 通用重大事实语义回归场景

需要保护的语义：

- 检索命中被截断时，模型不能把局部结果当作完整证据；
- 标的全年公司数据不能冒充购买日至期末并表贡献；
- 控制权日、实际并表日、报告期间和报表范围必须分别记录；
- 来源没有声明的时间、范围或口径标签不能由模型补造；
- `evidence.md`、`checkpoint.md` 和 `report.md` 的主张状态必须一致。

若未来实施，应设计一个新的最小场景执行器或使用当时已有的正式验收能力，输入只包含虚构事实
和来源元数据，输出必须真实包含证据、检查点和报告三类产物。Python 可以校验结构、字段存在和
安全边界，自然语言结论仍由独立审查者裁决。不得恢复历史代码精简中已删除的 conductor、
suite manifest、旧 fixture 协议、四路测试分类或历史结果封装。

### 10.2 强隔离真实盲测

普通"换一个模型再跑"不能证明候选没有读取正确答案、旧失败报告或根因说明。高风险语义变更
需要更强的隔离证据：

1. 候选只接收 canonical runtime Skill、宿主能力和中性请求；
2. 候选不可读取参考报告、历史裁决、正确数字、来源页码、缺失清单或修复设计；
3. 运行前记录实际 Skill 身份、模型、推理深度、工具能力和可见文件清单；
4. 运行使用新的工作根、空研究目录和全新会话；
5. 报告定稿后结束候选会话，不允许在看到裁决后恢复并补写。

强隔离适用于会改变证据规则、关键财务语义、安全边界或报告质量下界的高风险变更，不应成为
每次文案修改和普通代码清理的固定成本。

### 10.3 候选先锁定、参考后开放

候选生成结束后，应先保存并哈希：runtime 与 canonical 身份、固定请求字节、可见目录的前后
清单、`checkpoint.md`/`evidence.md`/`report.md` 和普通文件 artifacts、报告实际定稿时间和
环境信息。锁定完成后，独立审查者才能读取质量参考、历史错误和正确口径；评审逐项记录候选
定位、参考定位和具体理由，不能用总分让额外信息补偿事实错误，也不能直接修改候选报告。
该原则已被本文第 6.2 节部分承接，具体清单、隔离强度和审查角色仍需二期设计确定。

### 10.4 `INVALID` 与质量 `FAIL` 分离

未来评测应区分：

- `INVALID`：运行身份不明、隔离证据缺失、产物不完整、工具故障或请求不一致，无法据此评价
  产品质量；
- `FAIL`：运行有效且证据完整，但候选违反事实正确性、语义闭包、安全或质量门禁；
- `PASS`：运行有效，全部适用的不可补偿门禁通过。

`INVALID` 可以在修复环境后使用新编号和全新目录重跑；有效的 `FAIL` 必须保留原始产物，不得
在原目录碰运气或修补成 PASS。该区分防止把基础设施故障误归因于 Skill，也防止用重复运行
掩盖真实质量失败。

### 10.5 第二次全新环境复验

对于高风险语义变更，第一次有效 PASS 可能仍是模型偶然性。第二次复验应：使用新的 runtime
安装、工作根和会话；机械验证第一次产物锁，但在第二次锁定前不阅读其研究内容；使用逐字相同
的中性请求和相同的截止时点；独立完成第二次裁决后再检查是否存在产物复用或评审泄漏。是否
要求两次运行按变更风险决定：普通模板调整可用多模型集合验证，重大证据、安全或语义规则变更
才考虑强制两次隔离 PASS。

### 10.6 不可补偿质量门禁

保留两条简单规则，而不是恢复旧计划重复展开的检查矩阵：

1. 报告中已经写入的事实、数值、计算、单位、期间、主体、范围、时点和引用必须正确；任一会
   改变用户判断的错误不能由其他章节的数据量补偿；
2. 非重要公告可以省略，无法取得的内容可以明确写为未知，但不能猜测、补造或把"未检索"写成
   "没有"。

有效数据量按核心领域覆盖、可核查事实、时间序列、独立计算、重要事件、反证和监控规则判断，
不按行数、字数或重复表达判断。该原则已进入本文第 6 章，未来设计不再维护平行的质量维度清单。

### 10.7 可审计批准包

高风险变更提交用户批准时，可提供一个只读批准包，至少包含：变更范围和 canonical/runtime
身份、自动门禁结果、锁定候选及摘要哈希、实际报告时间和裁决时间、独立评审结论与已知问题和
适用边界、用户批准所绑定的准确提交。批准包只是让用户知道批准了什么，不发展成新的状态机或
长期资产数据库；普通阶段已有清晰路线图、报告和哈希时，不必额外复制一套材料。

### 10.8 使用规则

- 本章只提供设计输入，不新增已确认需求范围；
- 与第 2–9 章已确认需求重叠的内容，以那些章节为唯一 canonical owner；
- 只选择与当次风险直接相关的最小能力，不整体恢复旧质量加固流程；
- 实施前必须另写符合项目约定的需求、设计和执行计划，并重新取得用户批准；
- 未被后续设计选中的候选继续保持未实施状态。
