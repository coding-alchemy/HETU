# 大需求拆解与迁移方法论

> 文档版本：v1.1
> 文档状态：长期工程经验
> 创建／修订日期：2026-10-03
> 经验来源：HETU 五期拆解、迁移与收尾；harness-craft 分批迁移流程；用户 2026-10-03 流程补充
> 适用范围：大需求的分批交付，以及原开发分支已有成果的选择性迁移
> 文档性质：工程方法，不新增产品要求，不构成具体设计、执行计划或操作授权
> 项目约束：[AGENTS.md](../../AGENTS.md)

## 0. 适用条件

以可独立验收的用户结果划分批次，每批明确依赖、直接验收和排除范围。迁移采用：

**原开发分支保留存量 → 分批提取并汇入新建合并分支 → 全部改动拆解完成 → 在合并分支
统一整合、清理和评审 → 按授权合入主分支。**

合并分支从已核实的主分支新建，承接全部批次并作为后续提取的集成基线；需要本批迁移分支时，
从最新合并分支建立。每批通过只证明本批范围，各批不直接合入主分支。

只获授权拆解或规划时，完成范围与依赖梳理并交付，按 AGENTS.md 停在相应批准门；
仅获授权 rebase 时，核对实际状态与用户指定基线（合并分支或最终主分支）的内容后执行 §3 第 6 步，
不补做其他迁移步骤。
单个评审问题按已授权的最小范围修复，不因本方法新增设计、计划或审批阶段。

## 1. 已经无法收敛时，先恢复范围与状态

1. **核实存量。** 对照有效要求检查代码、Skill、测试和原始证据，分别列出已交付结果、
   实现缺陷、验收缺口、验收工具误判及待批准取舍。其他模型的报告作为线索，结论回源核对。
2. **区分成立范围。** 功能交付、受控行为证明、正式认证和性能达标分别判断；局部缺口只限制
   依赖它的结论，独立成立的成果保持有效。
3. **选择处置。** 真实缺陷按授权修复；现存证据充分时离线核对；证据不足时保留具体未满足项。
   降级、延期、例外或停止投入须有用户明确决定，原失败与原始 check 保留。
4. **选取下一批。** 从仍需交付的范围中选出满足 §2 的批次，明确其余内容去向，再进入迁移。
   已批准停止的范围保留事实与限制，不自动恢复执行或追加真实运行。

**完成条件：** 每项结果、缺口和取舍有具体依据，下一批与暂留范围清楚；没有把待批准处置当作通过。

## 2. 怎样拆成可独立交付的批次

优先在已有权威需求或计划中维护以下清单；文档新增及阶段划分按 AGENTS.md 的门禁处理。

| 字段 | 必须说清的内容 |
| --- | --- |
| 交付结果 | 用户在什么条件下能完成什么行为，承接哪些有效要求 |
| 依赖 | 兑现结果所必需的前置能力；依赖未就绪时怎样判定本批状态 |
| 直接验收 | 正例证明能力存在，反例证明必要边界生效；所需证据和通过条件 |
| 排除范围 | 哪些相关事项暂留、延期或停止，去向及批准依据 |
| 实现归属 | 所需实现、测试和使用文档；重叠文件具体到代码块或文档段落 |
| 状态与批准差异 | 当前完成程度、已批准取舍和仍需决定的事项 |

一个批次包含兑现结果必需的实现、测试与说明，执行顺序由依赖决定。
性能收益、扩大认证覆盖等独立目标可单列，但拆解不得擅自削弱原验收标准或把必要能力后置。
拆分完成后核查：严格执行本批内容能否达成所声明的用户结果；每项原要求是否已有明确去向。

## 3. 分批汇入合并分支与回收重复增量

以下步骤适用于原开发分支已有成果、需要分批迁移的任务。各步在已有授权范围内执行。

1. **核对并建立基线。** 查明原开发分支、主分支、远端引用、工作树和备份，记录完整 SHA 与共同祖先；
   按授权从已核实的主分支新建合并分支。未提交或未知改动先查清归属并保全。
   完成时能回查来源，且合并分支与本次可操作范围明确。
2. **建立提取清单。** 对本批相关文件标明整文件迁入、块级迁入、保持合并分支内容、暂留原分支或删除重复内容。
   交集文件逐块解释取舍；无法解释的差异先核查。完成时每项迁入内容均归属本批要求。
3. **统一修复来源。** 发现缺陷时按授权选定一个修复来源，在那里复现、修复和验证，再同步受影响实现
   与测试；避免两边分别维护不同修复。完成时同步内容一致，必要整合差异有解释。
4. **提取并验收。** 将本批内容按清单提取到合并分支；需要独立迁移分支时从最新合并分支建立。
   在迁移后的实际代码上检查规格符合性、
   仓库标准与用户行为。沿用有效证据，验证失败项及直接受影响的最小回归范围；股票分析和重跑遵守
   AGENTS.md 的成本与授权门禁。完成时已列阻断关闭、必要验证通过，未验证范围如实披露。
5. **交接并确认汇入。** 归并本批行为、兼容变化和验收限制，交付范围、相关 SHA、证据与剩余缺口；
   使用独立迁移分支时，按授权将其汇入合并分支。核实合并分支已包含本批最终内容；squash 合并用
   最终内容和范围比对，原迁移提交不是合并分支祖先不代表内容未迁入。
   完成时本批汇入事实可回查，主分支尚未接收本批增量。
6. **同步合并分支并审计。** 按授权将最新合并分支 rebase 回原开发分支；单独 rebase 任务以用户指定基线为准。
   操作前确认原开发分支工作树干净，创建不覆盖既有名称的备份引用。逐块解决冲突，保留基线已评审
   实现及原分支独有内容；对照备份确认没有第二套已迁移实现，未迁移代码、测试和规格没有误删或弱化，
   并验证冲突直接影响的行为。完成时所用基线是原开发分支祖先，
   剩余增量均有需求归属；推送按明确授权处理，改写远端历史时使用带预期 SHA 的 force-with-lease。
7. **重新盘点。** 下一批从最新合并分支与剩余需求重新确定范围，核对授权和证据适用性。
   分支、提交、模型、日期或哈希变化本身不使既有结果失效。全部待拆解改动均已迁入或有明确获批的
   排除去向后，进入 §4；原开发分支与合并分支差异为空只说明没有剩余增量，不能代替整体评审。

每个交接或停止点报告：本批结果与剩余范围、相关 SHA、直接验收、未解决问题、工作树与远端状态，
以及下一步所依赖的批准或合入事实。每轮结束后，已交付内容与待处理范围应能明确分开。

## 4. 合并分支整体整合、清理和评审

全部改动拆解完成后，先在合并分支完成以下工作，再进入主分支合并步骤：

1. **整体需求对照。** 对照有效的整体要求，核查所有批次汇合后的实现、依赖与批准差异；每项要求
   有明确实现和证据，未满足项保留准确状态。本批通过不能代替跨批组合结果成立。
2. **统一整合与清理。** 处理跨批接口、配置和规则冲突，归并重复实现、测试、规格与使用说明，
   清理失去用途的中间产物。保留有效行为、原始证据与恢复路径，范围内的清理不扩展为新功能或无关重构。
3. **整体评审与验证。** 在清理后的合并分支检查规格符合性、仓库标准及实际用户结果，重点核查跨批
   依赖与组合行为。复用有效证据，验证整合和清理直接影响的最小范围；关闭阻断项并披露剩余限制。
4. **交付并合入主分支。** 用户批准的整体交付范围成立，整合、清理和整体评审完成后，交付最终 SHA、
   相对主分支的增量、验证证据与未完成边界，再按明确授权合入主分支。合入后核对最终内容；如需同步
   回原开发分支，仍按相应授权与 §3 第 6 步处理。

**完成条件：** 主分支接收的是经过整体整合、清理和评审的最终内容；限定接受、停止投入和长期未完成
事实仍准确保留，不以合并成功宣称整体要求全部验收通过。

## 5. 收尾与计划生命周期

- **完成：** 本批用户结果与有效验收要求已满足；更新现行规格与使用说明，清理失去执行用途的计划并同步索引。
- **限定接受：** 保留用户批准的适用范围和例外，原始失败不改写；不能据此宣称更大范围完整通过。
- **待处理：** 必要验收、失败处置或批准尚未完成时保留计划与未闭合状态。
- **停止投入：** 用户明确决定停止后，按其授权清理计划；保留未验收事实和长期要求，不登记为验收通过。

长期文档维护最终行为、有效结论与限制；历史过程通过固定 Git 提交或可恢复归档回查。
临时分支在用途结束且独有历史已有恢复路径后，按清理授权删除。
