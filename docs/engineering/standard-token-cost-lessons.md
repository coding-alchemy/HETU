## 1. 核心经验

效果第一、成本第二；不通过削减 Q01–Q08、S01–S08、必要原文、风险发现、跨包判断或独立核对降本。
历史中存在可避免的调用，并不证明新增一段规则或一个 helper 就能省钱。需要分别回答：

1. 过去究竟发生了什么问题，涉及哪些有效工作？
2. 具体改法是否真的减少了目标动作，当前参考方式是否已经会合并？
3. 加上规则加载、核验、恢复和返工之后，完整可比窗口的实际输入是否减少？

工程通过、局部行为保持、净输入下降是三个独立结论。一次负结果可以完成获批的实验任务；
不能据此宣称降本目标完成，也不能把某个组合无收益扩大为整个方向无效。

## 3. 为什么历史机会没有变成本次收益

| 历史分析与假设 | 本次观察 | 后续参考 |
|---|---|---|
| 检查后直接返回完整诊断，消除单独读取 | A 候选计算并保存视图，但首回包仅摘要，下一工具才完整读取 | 函数正确和说明已写不等于实际执行已合并；先从真实轨迹核对目标动作是否消失 |
| 合并生成、等待、读取与结构探查 | B 参考和候选都已同轮完成 | 参考侧自然具备的行为不能算候选贡献，也不能故意拆弱参考来制造收益 |
| 聚合大量重复诊断减少回包 | A 候选仅 7 条诊断，视图 3,261B，大于自身原 JSON 的 2,732B | 聚合增加索引、计数和分组元数据；小样本未必抵消这些开销，不能外推大量重复诊断的情形 |
| 准确登记和兼容命令减少返工 | 未测得可比较的兼容错误减少；A 候选另有报告生成返工 | 历史错误确实存在，但不代表当前参考必然重犯；需要区分预防潜力与本次避免了什么 |
| 少量机械范例帮助执行 | 机械规则 5,669B → 13,393B，增加 7,724B，且发生回读；A 工具项 12→16，B 9→11 | 新规则每次加载有成本，收益却取决于是否实际消除操作；先考虑替换重复说明和使用现有入口 |

原分析覆盖 132 条用量事件、123 个唯一工具、301 个动作，确认长上下文中反复执行机械小步骤，
以及截断、格式返工等具体问题。≥300K 输入的 27 条事件占原新侧输入 40.83%；这只是分布，
不能将其全部认定可省。原分析把候选净收益标为未测，是正确边界；不足在于尚未证明
“新增范例”能稳定消除相应行为，后续方案又低估了规则加载和执行偏差。

本次只验证 O01/O06、O02、O04 的两个组合；O03 截断专项、O05 乱码预检、O07 自然交接、
O08 低价辅助没有在本批实施。它们保留为待评估方向，不按排序自动开展。

## 4. 后续分析和验证怎样更有用

### 4.1 先把调用的作用拆清

沿“动作 → 输入对象与实际读取范围 → 输出 → 作者实际读取 → 下游采用”定位，区分必要原文、
研究裁决和纯机械步骤。混合调用只优化确定的片段；例如生成回执与四份有效原文一起返回，
不能把整个调用视为无效。零增量、无工具事件和未知部分保留，不为凑节约删除。

分别记录原生 token、可见对象／送达内容字节、工具请求／返回容量。用途分类不能冒充完整
Prompt 组成；当时送达大小不能用当前磁盘文件大小替代；包装、文本、序列化和图片编码不相加。
用量累计值先差分、身份先去重，cached 是 input 子集，工具项和 CLI turn 都不是 API 请求数。

### 4.2 让候选对应实际动作变化

后续方案宜用一条具体链说明“原来怎样做、改后少哪一步、保留哪个判断点、增加哪些工作”。
历史涉及输入只是定位范围，不能作为预计收益。先用现有日志、确定性测试或静态检查核对
合并条件和额外加载量；它们能排除明显无效的改法，但不能代替获批后的真实行为与成本观察。

若参考侧已经自然完成合并，就如实收窄该候选的增量价值。若候选没有执行目标机制，就记录
“机制未兑现”，不要用工程单测代替，也不要据此宣布该机制本身无效。新规则尽量落在实际使用点，
避免为一个局部动作要求加载整套新材料；是否值得留下仍取决于用途和结果，不以规则短小推定收益。

### 4.3 材料应能检验所声称的机制

用中性任务和独立评分，保留真实参考行为。选择材料时说明它是否覆盖目标诊断规模、上下文阶段、
成功／失败分支和必要判断；小任务可验证原值和边界，未必能回答长上下文或大量重复诊断的收益。
这些差异应在结论中限制外推，不能通过人为削弱参考、泄露答案或删除异常来消除。

效果沿用有效验收，只核直接受影响的最小范围。能力缺失或共享投入不可观察时，报告具体限制；
不把成本任务转回股本补件、筛公司或 G2，不自行新增完整股票研究或对照。

### 4.4 完整记录净变化，及时结束负结果

固定双方任务、材料、模型设置、终止条件与窗口；新增规则加载、回读、失败及修正都计入。
共同投入另列，可得则记录，未知不填零；缺完整窗口时不能宣称完整净收益。实际金额未知就只报
input／cached／uncached／output，不根据模型标价或字节猜账单。

先检查效果，再看实际输入差额。没有收益的候选不默认推广；额度用完按既定结论结束，
不调样本或反复试跑追求正结果。已知合同缺口应写为未满足，不能用机械 PASS 或“未证”淡化。
