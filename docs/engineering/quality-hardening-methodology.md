## 0. 方法结论

质量加固不是增加更多规则，而是为真实风险建立完整证据链：

> 真实失败 → 唯一 owner → 最小规则或确定性 seam → 正负行为证据 → 锁定真实运行 → 人工内容验收 → 删除失效资产。

每种证据只回答自己能证明的问题。结构完整、测试全绿、机械 `PASS`、来源可访问和工具可解析，
都不能单独证明用户结果正确。二期在 997 项测试通过后仍单列真实报告验收缺口；三期在 1024 项
测试之外完成双模型真实报告与人工内容验收，才闭合用户可观察结果。

本方法假设已有可复现的现行行为。若目标是新增产品能力、改变业务范围或重建架构，应另行进入
需求与设计流程，不以“质量加固”名义实施。

## 1. 何时启动加固

只有同时满足以下条件，才把问题纳入质量加固：

1. 已观察到具体失败，或有直接证据证明失败会发生；
2. 失败会影响用户判断、事实正确性、时点、范围、安全、授权或可追溯性；
3. 能指出负责取得、判断、修正和传播结果的 owner；
4. 能定义修改前后可直接观察的差异。

格式偏好、单次模型措辞差异、没有消费方的抽象完整性，以及“以后可能需要”的扩展点，不足以
启动加固。

## 2. 五条原则

### 2.1 从失败行为出发

先保存失败输入、产物和用户影响，再把问题写成可观察行为，例如“分页未闭合时不得断言无公告”，
而不是“提高准确性”。只修复已确认的失败模式；换主体、期间或模型复验，防止把答案硬编码进规则。

### 2.2 规则靠近唯一 owner

事实由一个 owner 取得、核验、解释和回访，其他环节只消费其当前结果。上游修正时，同步更新产物
状态、输入链、直接引用和受影响下游；不能只改 `report.md`。唯一 owner 约束事实归属，不禁止并行取证。

### 2.3 语义判断与确定性工作分离

Agent 负责来源适用性、冲突裁决、因果分析和写作；脚本只处理显式输入的采集、解析、标准化、
精确计算和机械校验。确定性工具应单次原子执行、保留原值与输入哈希、可离线重放、拒绝覆盖，
且不自动换源、不猜字段、不改写冲突值、不生成业务结论。

### 2.4 未知、失败和状态转换必须真实

可访问不等于获授权，可解析不等于适用，某次采用不等于长期稳定，检索未命中不等于不存在，
新产物正确也不等于旧产物已退出采用。完成压力不得把“未发现”“未取得”“候选”“存在冲突”
或 `warning` 升级为成功。

追溯链用于回答结果来自哪里、审查的是哪次运行以及评审后是否被改写；哈希只证明同一版本的身份
和完整性，不用于报告质量评分或跨模型排名。

### 2.5 证据分层，门禁按用户影响分级

静态合同证明规则存在；单元与负向测试证明确定性行为；重放证明同一输入可复算；检查器证明结构
与追溯可机械复核；隔离真实运行证明完整系统可工作；人工验收证明内容可交付。各层互不替代。

事实、时点、安全和授权问题阻断交付；覆盖或追溯限制需披露并收缩结论；纯格式问题只保留提示。
保护建立后，删除失去消费方或唯一保护职责的旧实现、测试和迁移设施，避免加固体系无限增长。

## 3. 六步闭环

| 步骤 | 动作 | 直接产物与门禁 |
| --- | --- | --- |
| 1. 定义失败 | 写明错误行为、用户影响和必须守住的边界 | 可观察的失败条件与成功条件 |
| 2. 冻结样本 | 保存原始输入、失败产物、运行身份和中性请求 | 请求不泄露答案，样本可复现 |
| 3. 指定 owner | 定位负责事实或行为的工作包、合同、工具或发布环节 | 只有一个裁决 owner，无平行控制面 |
| 4. 最小修改 | 语义规则写入 owner；只有机械问题才增加原子工具或检查 | 每个改动都能回链已确认失败 |
| 5. 建立反证 | 运行正例、错单位／跨时点／截断输入等负例，并删除关键规则试跑 | 能力存在时通过，能力缺失时失败 |
| 6. 真实验收 | 全新目录和会话运行代表性样本，先锁定再评审；记录限制并清理失效资产 | 内容与用户验收通过，无未披露阻断项 |

## 4. 完成门禁

宣布加固完成前，逐项回答：

| 门禁 | 完成证据 |
| --- | --- |
| 核心结果 | 严格执行当前规则不会仍然错过用户可观察目标 |
| 行为因果 | 删除关键规则或能力后，测试可靠失败且输入不泄露答案 |
| 机械完整性 | 输入链、产物状态、引用、错误码、安装副本和锁定记录一致 |
| 真实效果 | 至少一次全新代表性运行直接证明结果改善；高风险变更按需使用多模型 |
| 状态诚实 | 未取得、冲突、授权限制和非阻断提示均保留真实状态 |
| 范围守恒 | 没有新增未要求能力、平行架构或影子归档；失效资产已删除或有明确保留理由 |

任一项缺少直接证据，只能报告进展与缺口，不能用其他层的全绿结果补偿。

## 5. 五类反模式

1. **代理指标冒充质量：** 用测试数、覆盖率、行数、哈希、机械 `PASS` 或总分代替内容正确性。
2. **静态存在冒充行为：** 只检查 Prompt 有某句话，不验证正负场景中的实际决策。
3. **状态升级：** 把来源存在、网页可见、已有适配器、未发现或某次采用扩大为正式、完整或长期可用。
4. **局部修补：** 只改最终报告，不更新 owner、旧产物状态、输入链和下游引用。
5. **过度建设：** 为单个失败新增状态机、通用平台、插件系统、工作包、兼容层或仓库内 archive。
