# 不变量保护式代码精简方法论

> 文档版本：v1.0
> 文档状态：长期保留
> 方法名称：保护性减法（Invariant-Preserving Code Reduction）
> 经验来源：HETU 个股分析工作流三期代码精简
> 适用范围：已有可用产品、工作流、Skill、Agent 或服务的代码和资产减量
> 文档性质：通用工程方法论，不构成具体项目的需求、设计或执行计划

---

## 0. 方法结论

代码精简的目标不是删除最多的文件，而是在不降低现有产品价值的前提下，删除已经失去消费方、
保护职责和现行契约价值的实现与资产。

本方法遵循一条核心原则：

> 先冻结必须保留的产品不变量，再分阶段删除实现；删除责任在删除方，无法证明安全就保留。

“代码更少”只是结果，不能覆盖正确性、安全性、用户可见效果、可回退性和证据完整性。精简过程
不得借机增加功能、重构保留主线或降低测试断言。

## 1. 适用边界

### 1.1 适用场景

本方法适用于：

- 产品已经存在可运行、可验证的当前主线；
- 仓库积累了中间产物、迁移设施、旧实现、历史计划或孤立依赖；
- 精简必须证明用户可见效果没有退化；
- 系统包含非确定性输出，无法使用逐字结果比较；
- 清理需要分阶段执行，并在阶段之间设置人工批准门。

### 1.2 不适用场景

本方法不用于：

- 借精简名义进行架构重写、性能优化或功能增强；
- 尚未形成稳定产品行为的新项目；
- 已经明确接受行为变化的破坏性版本升级；
- 仅整理格式、命名或代码风格的普通重构；
- 通过降低质量门槛换取代码量下降。

## 2. 三个基本模型

### 2.1 产品不变量模型

开始清理前，先定义不能退化的产品价值，而不是先罗列“看起来无用”的文件。不变量通常包括：

1. 用户可见入口、正常请求和输出；
2. 核心业务语义和关键质量下界；
3. 安全、授权、隐私、错误处理和失败关闭边界；
4. 安装、发现、配置、manifest 和分发契约；
5. 当前仍承诺的兼容能力；
6. 对上述行为提供唯一保护的测试和文档。

真正需要逐字节冻结的权威实现，可以记录路径、文件模式、文件集合和内容哈希。不是权威实现的
普通代码不应为了方便而一并冻结，否则会把可删除实现错误地转化为永久约束。

### 2.2 三层证据模型

每个清理阶段必须同时具备三类证据：

| 证据层 | 证明内容 | 常见手段 |
|---|---|---|
| 内容身份 | 权威实现没有被修改或替换 | 路径、模式、数量、SHA-256、目录洁净检查 |
| 自动行为 | 当前入口、边界和工程契约仍然成立 | 测试、静态检查、链接、CLI、安装、导入与安全门禁 |
| 真实效果 | 用户实际使用时没有出现共同退化 | 固定真实请求、语义基线、盲测和人工批准 |

三层证据不能互相替代。自动测试通过不能证明真实输出仍然可用；人工结果可用也不能接受权威内容
变化、安全门禁失败或安装包污染。

### 2.3 删除举证模型

候选内容只有在以下事实都成立时才能删除：

1. 不属于权威产品实现或必需资源；
2. 不在运行入口、正常调用链、安装或分发路径中使用；
3. 不承担现行行为或安全边界的唯一保护作用；
4. 不是当前有效需求、设计决策或用户契约的唯一记录；
5. 删除后能够通过自动检查和真实效果验证；
6. 当前阶段能够准确回退。

文件较旧、位于测试目录、一次搜索没有引用或“以后大概不会用”都不是充分的删除依据。

## 3. 候选识别与裁决

### 3.1 四面消费审计

每个候选至少检查四个方面：

| 审计面 | 需要回答的问题 |
|---|---|
| 运行与导入 | 是否被入口、调用链、动态导入、插件发现或反射机制消费？ |
| 安装与分发 | 是否被 manifest、CLI、package data、配置加载或安装脚本消费？ |
| 测试职责 | 是否是某个现行不变量的唯一保护？是否只证明历史实现或迁移过程？ |
| 文档与契约 | 是否仍被当前需求、设计、用户文档或外部承诺依赖？ |

一次文本搜索只能提供线索。还应结合导入图、入口注册、构建配置、安装产物、测试职责、动态机制
和文档链接判断。对于动态加载较多的系统，需要通过运行或安装验证补足静态搜索的盲区。

### 3.2 统一决策表

| 候选状态 | 处理原则 |
|---|---|
| 有当前运行、安装或分发消费方 | 保留 |
| 唯一保护现行行为 | 保留，或先迁移最小必要断言 |
| 只保护已退场实现 | 与退场实现一起删除 |
| 只记录开发过程或一次性迁移 | 删除，通过 Git 历史追溯 |
| 有明确、近期且已立项的复用价值 | 与当前运行路径隔离，交由后续独立需求处理 |
| 只有“以后可能有用” | 原则上删除，不在仓库内建立影子归档 |
| 证据冲突或无法判断 | 默认保留 |

可以把删除条件概括为：

> 可删除 = 无产品消费方 + 无唯一保护职责 + 无现行契约价值 + 可验证消失 + 可准确回退。

### 3.3 风险排序

候选应按产品耦合、验证难度和回退成本从低到高排序，而不是机械按目录删除。经过 HETU 三期验证
的通用顺序是：

1. 生成结果、日志、调试导出和中间产物；
2. 一次性迁移账本、开发期 harness、fixture 和专用测试；
3. 已明确退场的旧实现及其完整依赖闭包；
4. 已完成、被替代且不再作为当前依据的历史执行计划；
5. 前序删除后暴露的孤立脚本、分类器、依赖、配置和重复文档。

旧实现退场通常是风险最高、边界变化最明确的一类，应作为独立阶段，不能混入测试、文档或依赖
清理。剩余冗余审计必须最后执行，因为很多孤立内容只有在主依赖闭包删除后才能被准确识别。

## 4. 分阶段执行协议

### 4.1 建立可复现基线

首次删除前至少记录：

- 分支、提交和工作树状态；
- 权威实现的内容指纹；
- Git 跟踪文件的文件数、文本行数和字节数；
- 当前测试、静态检查、文档检查和安装结果；
- 可重复的真实请求及其语义验收基线；
- 证据文件的相对路径、实际生成时间和摘要哈希。

规模统计必须始终使用同一口径。虚拟环境、缓存、下载文件和其他未跟踪环境体积不应混入仓库
减量数据。

### 4.2 阶段事务

每个阶段采用相同闭环：

```text
冻结拟删、拟留和存疑清单
    → 记录开始提交、工作树、规模和指纹
    → 只实施当前风险类别
    → 运行阶段专项检查
    → 运行共同自动门禁
    → 复核指纹并统计阶段及累计减量
    → 执行固定真实请求
    → 停止并等待人工批准
    → 批准后才关闭阶段并进入下一阶段
```

每个阶段应形成一笔独立、可审查、可准确逆向恢复的变更。一次批准只适用于当时的提交、证据和
真实结果；后续变更不能复用旧批准。

### 4.3 范围防火墙

阶段实施时必须遵守：

- 只修改当前阶段明确批准的范围；
- 不顺手重构相邻代码、文档或命名；
- 不增加替代框架、兼容层、迁移器或新功能；
- 当前改动造成的孤立项可以一并清理，既有无关问题只记录不处理；
- 自动门禁失败时不得继续运行真实效果验证；
- 未取得人工批准前，不准备或实施下一阶段删除。

## 5. 测试与门禁精简

### 5.1 按保护对象决定测试去留

测试数量和覆盖率不是产品价值。测试去留应建立“当前不变量 → 保留测试”的映射：

- 直接保护当前行为、安全和安装契约的最小测试保留；
- 只证明迁移过程、旧节点数量、旧包装器或退场实现的测试删除；
- 同时包含现行保护和历史结构的测试，只迁移最小必要断言；
- 不复制旧 harness、fixture 协议、状态机或分类体系；
- 不通过删除失败测试、降低断言或修改权威实现来迁就删除。

如果待删测试是某个现行不变量的唯一保护，应先把必要断言迁入最近的现有测试，再删除历史设施。

### 5.2 最终门禁应是薄编排层

最终全量门禁只负责编排已有检查，不复制测试、manifest 或文档校验逻辑。门禁名称和命令应反映
当前产品，不继续携带已经结束的阶段名称、四路分类或历史覆盖率协议。

## 6. 旧实现与依赖闭包退场

删除旧实现时，应把它作为完整依赖闭包处理：

1. 先定义删除后的公共入口和允许命令；
2. 使用测试观察旧契约仍然存在的失败；
3. 删除入口注册、源码、专属测试、fixture 和 package data；
4. 删除只服务旧闭包的生产和开发依赖；
5. 同步更新当前文档和直接文档断言；
6. 验证保留入口正常、旧入口失败、旧模块不可导入；
7. 在全新环境中验证分发文件和依赖确实收缩。

不要为已经获准退场的能力增加兼容 shim、归档包或迁移命令。Git 历史已经承担历史实现的追溯
职责。

## 7. 非确定性系统的效果验证

大模型、搜索、推荐等系统的输出存在自然波动，不能要求每次结果逐字相同。应改为比较稳定的
行为与语义主干：

1. 固定输入、运行模式、深度、截止时点和重点；
2. 固定必须保留的任务边界、核心事实关系、反证、安全和不确定性要求；
3. 使用多个独立运行样本，避免单次随机波动主导结论；
4. 比较报告集合是否保留语义主干，不比较措辞、标题和篇幅；
5. 单个模型的孤立错误或遗漏先记录为模型噪声；
6. 两个或更多模型出现同方向核心退化时，再调查是否由删除引入；
7. 必要时在上一通过提交补跑控制样本；
8. 最终是否放行仍由用户依据真实结果裁决。

代码精简验证只回答“删除是否影响主要逻辑”，不承担产品全面质量改进。发现的既有质量问题应
记录并转交独立阶段，避免精简任务演变为无限质量加固。

## 8. 安装、依赖与消失证明

仓库内测试通过不能证明安装产物已经精简。最终应在全新环境中同时证明：

- 保留模块、CLI、Skill 或服务入口能够正常运行；
- 安装后的权威内容与仓库 canonical 内容一致；
- 已删除模块无法导入，旧入口不可调用；
- 分发文件清单不再包含已删除路径或 package data；
- 已删除依赖在新环境中确实不存在；
- 依赖检查通过，没有隐式依赖或缺失依赖；
- 当前文档、帮助文本和实际公共能力一致。

“保留模块可以导入”只能证明正向路径，必须再用负向导入、分发清单和依赖不存在检查证明删除
真正生效。

## 9. 失败、回退与证据恢复

### 9.1 自动失败

自动门禁失败时不进入人工验证。应定位当前阶段的最小问题项，恢复该候选或补足只保护现有行为
的最小测试，然后重新运行完整阶段门禁。

### 9.2 真实效果失败

真实结果退化或用户拒绝时，当前阶段保持未通过。优先恢复最小可疑项；无法可靠定位时，逆向回退
整个阶段。无法证明安全的候选永久退出本轮精简范围。

回退应使用可审查的逆向变更，不使用破坏性历史重写。后续阶段失败不自动撤销已经批准的前序
阶段。

### 9.3 证据失效

若指纹、规模快照、自动日志或真实报告丢失、为空或哈希不符，不能沿用路线图中的旧结论。应从
记录的提交重新建立隔离环境，重跑完整门禁和真实请求，并重新取得批准。

## 10. 完成标准

只有同时满足以下条件，代码精简才能完成：

1. 所有阶段按风险顺序执行并取得明确批准；
2. 权威实现、核心效果、安全、安装和必要 helper 没有退化；
3. 所有候选均已删除或记录具体保留理由；
4. 最终包、入口、依赖、测试和文档与当前产品一致；
5. 已报告各阶段和累计文件、行数、字节及依赖变化；
6. 全新安装环境证明保留项可用、删除项确实不存在；
7. 工作树干净，没有混入后续功能、无关重构或影子归档。

## 11. 常见反模式

执行类似精简时，应避免：

- 为达到预设删除比例而扩大范围；
- 把文件年龄、目录名称或单次无引用搜索当作删除证明；
- 把测试数量、覆盖率或仓库体积当作效果等价证明；
- 一边删除，一边优化保留主线或增加新功能；
- 为历史代码增加新的兼容层；
- 把死代码整体移动到仓库内的 archive，制造另一种冗余；
- 要求非确定性输出逐字一致；
- 用单个模型的一次异常否定或放行整个阶段；
- 自动门禁通过后跳过真实使用验证；
- 在人工批准前提前实施下一阶段。

## 12. HETU 验证结果

HETU 三期使用本方法完成了从开发期重资产仓库向 Skill 主线仓库的收缩：

| 指标 | 清理前 | 清理后 | 减少量 | 减少比例 |
|---|---:|---:|---:|---:|
| Git 跟踪文件 | 396 | 113 | 283 | 约 71.5% |
| 文本行 | 96,044 | 23,745 | 72,299 | 约 75.3% |
| 字节 | 4,820,570 | 1,168,064 | 3,652,506 | 约 75.8% |

同时满足：

- canonical Skill 20 个文件的指纹在全部清理阶段保持一致；
- 最终 424 项测试及静态、文档和 Skill 校验通过；
- 干净安装验证了当前 CLI、Skill、helper、负向导入和依赖边界；
- 每个清理阶段均建立独立规模、指纹和真实效果证据；
- 多模型语义对照未发现由删除造成的共同核心退化。

本案例证明该方法能够支持大规模减量，但不意味着其他项目可以复制 HETU 的目录、文件数量、
模型数量或固定请求。可复用的是不变量、证据、风险排序、阶段事务和回退原则。

HETU 精简后的产品边界见
[个股分析工作流 V1 一期实现](../specs/2026-08-17-stock-analysis-workflow-v1-phase-1-implementation.md)；阶段计划、原始门禁和
逐阶段裁决只通过 Git 历史追溯，不作为本方法论的当前依赖。

## 13. 可复用检查清单

### 清理前

- [ ] 当前产品主线和非目标已经明确；
- [ ] 产品不变量和权威实现已经冻结；
- [ ] 内容、自动行为和真实效果三层基线已经建立；
- [ ] 候选完成运行、安装、测试和文档四面审计；
- [ ] 阶段顺序按风险而不是目录确定。

### 每个阶段

- [ ] 拟删、拟留和存疑项已经记录；
- [ ] 变更只包含当前阶段范围；
- [ ] 专项检查和共同自动门禁通过；
- [ ] 权威内容指纹与基线一致；
- [ ] 阶段和累计减量使用统一口径记录；
- [ ] 真实效果完成独立验证；
- [ ] 已停止并取得明确人工批准。

### 最终关闭

- [ ] 全新安装环境验证通过；
- [ ] 已删除入口、模块、文件和依赖确实不存在；
- [ ] 当前入口、文档和分发内容一致；
- [ ] 所有保留候选都有具体理由；
- [ ] 没有混入新功能、无关重构或影子归档；
- [ ] 工作树和阶段证据完整、可复核。
